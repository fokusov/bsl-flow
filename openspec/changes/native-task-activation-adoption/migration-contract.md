# Explicit legacy adoption and rebind v1

Нормативный контракт дополняет design.md. Spike в `work/blocked-completion-20260912/adoption-contract.md` — источник наблюдений, а не дополнительный протокол: отдельные reservation/fence journals, circular hashes и обязательный current.json из него не принимаются.

## Команды и пользовательское решение

`task adopt --project <clone worktree> --source <legacy worktree> --task <uuid> --preview` выводит read-only plan JSON. `--apply --input <saved plan.json>` переносит только эту задачу. `task rebind --project <current exact root> --task <same uuid> --expected-revision <n> --input <full trusted request.json>` создаёт новую execution binding после переноса. Пакетный `--all` не нужен.

Пользователь явно выбрал сохранение UUID/истории с перепривязкой и проверками актуальности перед продолжением. Adopt не запускает controller/provider/runtime. Rebind не продолжает старый process: он проходит activation preflight, сохраняет исторические доказательства и начинает актуальный маршрут с inspect. Source, policy, criteria и engine bindings пересчитываются. Старая completed/accepted history остаётся историей и не удовлетворяет новым gates.

## Eligibility и identity

Source и project должны быть проверенными worktree одного Git common dir. Source требует полного contiguous v1 journal и совпадения сохранённого project_path с exact source root, как в существующем Read-BFTask; произвольная перемещённая копия с чужим project_path не становится действующим source owner. Apply запрещён для running, active_attempt, unresolved_effect, живого/неоднозначного retained process, task-local незавершённого publication intent, pending native target либо иной незавершённой внешней операции. Сначала выполняется сверка существующим владельцем, затем новый preview. Ownership не передаётся в состояние, из которого прежний controller уже не сможет выполнить нужное recovery.

Для publication проверяются существующие task-local `publications/<id>/request.json`, `intent.json`, `published.json` и соответствующий machine-local pending marker, вычисляемый по текущему контракту. Для native1c — точный target-key/pending по сохранённым native receipts. Неизвестное расположение/состояние после возможного dispatch блокирует apply; никаких broad disk scans, remote reads либо вызовов 1С. Наличие старого completed status не заменяет проверку pending.

Все same-UUID legacy copies должны иметь одну verified semantic history; corrupt/unreadable/divergent copy блокирует apply. Сохранение истории не меняет прежнюю семантику canonical JSON: whitespace/key-order variants не создают другой task UUID. Exact source выбран явным --source; его raw bytes фиксируются preview и копируются без изменений. Другие одинаковые semantic copies перечисляются с provenance и hashes; raw drift выбранного source после preview блокирует apply. Для native discovery после переноса legacy copy должна совпадать с сохранённым semantic prefix и своим сохранённым raw/artifact binding, если он был зафиксирован.

`sources` всегда включает все обнаруженные same-ID copies, включая выбранный source; для каждой фиксируются собственные raw/artifact bindings. После переноса оставшаяся copy из этого списка должна сохранять оба binding. Новая обнаруженная copy вне списка допускается как исторический duplicate только при совпадении verified semantic prefix и raw/artifact binding одной из сохранённых copies; иначе это диагностируемый conflict. Удалённая copy не создаёт conflict: сохранённая provenance и скопированные evidence остаются доступны. Raw drift даёт конфликт содержимого известной copy, а не новую identity задачи. Во всех случаях списки показывают один UUID и диагностику; targeted execution блокируется, пока конфликт не разрешён.

## Один journal и переносимые bytes

Target: `<git common dir>/bsl-flow/tasks/<uuid>`. Он содержит исходные v1 `revisions/000001.json…N.json` byte-for-byte, затем v2 continuation N+1. `previous_sha256` N+1 равен существующему semantic canonical hash v1 revision N. Raw revision hashes сохраняются отдельно. Mixed chain валидируется существующим dual-reader с новым closed controller branch; первичная копия не является вторым authoritative legacy segment.

Continuation N+1 имеет ровно существующие outer v2 fields `schema_version`, `task_id`, `revision`, `previous_sha256`, `title`, `description`, `priority`, `labels`, `depends_on`, `lifecycle`, `archived`, `created_at`, `updated_at`, `provenance`, `controller` и обязательное для mixed chain поле `migration`. Значения: schema_version=2, revision=N+1, тот же task_id, lifecycle=controller, archived=false, title=`(legacy v1 task)`, description пустая, priority=low, labels/depends_on пустые. Provenance: source=`legacy_adoption`, reference=`task:<uuid>`, created_in=source_root; ограничения существующего metadata schema проверяются до publish. created_at сохраняет v1 значение, updated_at равен committed_at receipt. Controller копирует все execution fields v1 N согласно закрытому mapping design.md, включая исторические status/stage/evidence, и получает engine=null. Mapping не добавляет dispatch или acceptance. Transition v1→v2 допустим ровно один раз при полном valid receipt/plan/manifest, неизменном v1 prefix и requires_rebind=true. Любая v1 revision после N+1, второй transition или mixed chain без migration binding запрещены. Последующие v2 revisions сохраняют immutable migration references; только trusted rebind меняет requires_rebind на false.

Неизменяемые task-local inputs/attempts/acceptances/delivery/publication/review/budget artifacts копируются в `legacy/artifacts/<source-relative-path>`; исходные absolute references внутри JSON не переписываются. Manifest сопоставляет exact original path с canonical relative path и raw SHA-256. Исторический resolver разрешает только объявленные проверенные файлы, никогда произвольный prefix substitution или escape. Missing внешний live path отображается как stale; source trees, executables, machine journals, queues, auth homes и credentials не копируются рекурсивно. Missing/changed обязательный task-local evidence даёт blocker.

Walker использует bounded regular-file streaming и safe no-symlink/reparse traversal; `.writer.lock`, generated current.json, temporary/unfinished files и известные auth/credential assets исключены с причиной. Если исключённый файл требуется immutable evidence binding, apply блокируется. Raw evidence остаётся private; публичные projections не выводят prompts, credentials или raw provider bodies.

## Закрытые документы

Plan имеет ровно `schema_version=1`, `contract=bsl-flow.legacy-adoption.v1`, `task_id`, `source_root`, `common_dir`, `repository_id` (null допустим только пока identity отсутствует), `prefix_revision`, `prefix_semantic_sha256`, `sources`, `manifest`, `dependencies`, `eligibility`, `blockers`, `binding_sha256`. Source entries: `root`, `prefix_semantic_sha256`, `raw_manifest_sha256`, `artifact_manifest_sha256`. Manifest: `revisions`, `artifacts`, `external_refs`, `excluded`. File entries: `source_rel`, `canonical_rel`, `size_bytes`, `raw_sha256`, optional `semantic_sha256` только для revisions. External refs/exclusions: `path`, `reason`. Unknown fields, duplicate keys, unsafe paths, invalid types/hashes/UUID отклоняются. Binding hash вычисляется canonical encoder по plan без самого `binding_sha256`; timestamp не входит в identity.

`dependencies` имеет ровно `baseline`, `request_sha256`, `intent_sha256`, `policy_sha256`, `execution_profile_sha256`: первые четыре значения берутся из validated v1 revision N (`baseline`, `request_hash`, `intent_hash`, `policy_hash`), последнее равно H(request.execution_profile) либо null при отсутствии profile. Это исторический snapshot, а не доказательство current freshness; apply проверяет совпадение с тем же v1 N, rebind измеряет актуальные зависимости отдельно. `eligibility` имеет ровно boolean `eligible` и object `checks` с boolean keys `source_owner`, `journal`, `siblings`, `inactive`, `processes_terminal`, `publications_clear`, `native_targets_clear`, `artifacts_complete`, `target_available`. True означает проверенное выполнение условия, включая проверенное отсутствие применимой операции; неизвестность даёт false. `eligible` равно конъюнкции checks. `blockers` — array непустых bounded строк с конкретным BF_BLOCKED/BF_CONFLICT/BF_INVALID reason; при eligible=true массив пуст, при false непуст. Ни один check не заменяется переданным пользователем true: apply повторно вычисляет их из source/target.

`adoption-receipt.json` имеет ровно `schema_version=1`, `task_id`, `plan_sha256`, `manifest_sha256`, `repository_id`, `prefix_revision`, `prefix_semantic_sha256`, `continuation_revision`, `committed_at`. Manifest хранится отдельно как `legacy-artifact-manifest.json`. Нет взаимного receipt↔fence hash. Если preview видел repository_id=null, apply создаёт/валидирует identity для того же canonical common dir; существующий непустой ID из preview обязан совпасть. Paths/clone identity и receipt проверяются повторно, отсутствие ID не разрешает другой clone.

Exact approved plan сохраняется как `adoption-plan.json`; это immutable input artifact, а не журнал операций. Receipt.plan_sha256 связывает его bytes. Historical resolver восстанавливает original absolute path только как safe Join сохранённого plan.source_root и manifest artifact.source_rel, проверяет точное совпадение исходного reference и затем читает указанный canonical_rel/hash. Никакая часть исходного абсолютного пути не заменяется эвристически. При preview repository_id=null повторная проверка apply сохраняет этот null в сравнении исходного plan binding, независимо от уже созданного actual repository ID. Actual ID записан в receipt и обязан совпадать с текущим store; остальные поля и verified common dir проверяются без послабления.

Формулы и ordering: `H(value)=repository.Hash(value)` — SHA-256 существующего canonical JSON encoder (тот же контракт Get-BFHash), `R(bytes)=SHA-256 bytes`. `prefix_semantic_sha256=H(v1 revision N)` только после полной проверки contiguous revisions 1..N и всех previous_sha256 links; это существующая semantic identity legacy reader. Предыдущие revisions транзитивно связаны хешами, поэтому другой valid semantic prefix не может иметь тот же terminal hash без SHA-256 collision. Новый hash-of-hashes для identity не вводится. `M(root)` — manifest, построенный одинаковым bounded walker для task directory в данной verified copy. Для sources entry `raw_manifest_sha256=H(M(root).revisions)`, `artifact_manifest_sha256=H(M(root).artifacts)`. Полный M хранится только для выбранной copy как plan.manifest=M(plan.source_root); для sibling хранятся root и оба digest, а проверка заново строит M(root) и сравнивает digest. Отдельного скрытого source.manifest поля нет. `binding_sha256=H(plan без binding_sha256)`. Manifest arrays revisions сортируются по номеру revision, artifacts по source_rel, external_refs/excluded по path затем reason; строковые сравнения ordinal, slash в relative paths `/`, canonical_rel однозначен. Повторные source_rel/canonical_rel или case-colliding filesystem paths запрещены, sources сортируются по canonical absolute root. `adoption-plan.json` и `legacy-artifact-manifest.json` записываются canonical bytes без BOM/новой строки; receipt.plan_sha256=R(plan bytes), receipt.manifest_sha256=R(manifest bytes). Outer migration.receipt_sha256=R(receipt bytes), migration.manifest_sha256=receipt.manifest_sha256. Receipt записывается canonical bytes. Во всех сохранённых copies hashes пересчитываются из фактических bytes; имя файла/current projection не заменяет проверку.

V2 outer state допускает optional closed `migration={receipt_sha256, manifest_sha256, prefix_revision, requires_rebind}`. Для новой импортированной history requires_rebind=true; controller сохраняет исторические execution fields, но engine=null. Это единственный допустимый null engine case, требующий валидного migration receipt. Любой native execution/acceptance возвращает next_action=rebind до успешного trusted rebind. После rebind engine заполнен действительным контрактом, requires_rebind=false, intent/authorization revisions увеличены, status=ready; исторические entries сохраняются и считаются stale по новым bindings. Read projections показывают исторический status и отдельный binding_state=rebind_required/current.

## Публикация и конкуренция

Apply использует существующий repository graph lock (как create/edit/archive) и source `.writer.lock` всех выбранных same-ID copies в сортированном порядке. Повторно проверяет target, source/manifest/eligibility под locks. Native same-ID write не допускается, пока apply удерживает graph lock; новые metadata creators сериализуются тем же lock. После crash/release lock другой creator может занять отсутствующий target: повтор apply обнаруживает чужой target и возвращает conflict, без overwrite. Долгоживущей reservation здесь нет. Staging расположен вне tasks/, под `adoption/<binding_sha256>/staging/<uuid>` для использования существующего task-ID reader; он не является видимой задачей или отдельным dispatcher.

В staging создаются все immutable files, manifest, receipt и validated mixed chain с continuation. После проверки hashes/containment/transition целый task directory атомарно публикуется в отсутствующий target; чужой target никогда не заменяется. current.json строится как derived projection и не является условием истинности journal. Crash/rename-sync uncertainty разрешается control read exact target/receipt/manifest. Уже опубликованная revision не переписывается ради missing current.json.

Повтор того же plan сверяет immutable prefix, receipt и перенесённые artifacts и возвращает существующий результат без новой revision. Более поздние native revisions не мешают idempotence и не откатываются. Partial staging с тем же binding может дополняться только после полной revalidation; неизвестные/чужие bytes сохраняются и блокируют publish. No cleanup не превращает uncertain target в отсутствующий. Source/target drift даёт conflict.

`eligibility.checks.target_available=true` означает отсутствующий target либо подтверждённый exact committed target с тем же plan/receipt/manifest/prefix; foreign/corrupt/partial target даёт false. Apply сначала проверяет возможный committed-repeat по canonical evidence и current repository identity. Для подтверждённого repeat удаление прежнего source worktree/copy не требует нового переноса и не блокирует возврат результата; все ещё существующие saved copies проверяются на drift. Отсутствующий source запрещает только незавершённый/новый перенос. Такой repeat не переписывает saved plan. Неверная текущая native chain остаётся диагностируемой ошибкой и не исправляется повторным apply.

## Legacy writer guard

Обновлённый packaged legacy writer проверяет canonical UUID в verified common dir до изменения task-local файлов и повторно под source `.writer.lock`. Любая canonical directory резервирует UUID, даже если receipt/state повреждены: запись legacy запрещена с указанием native owner. Проверка применяется к task writes через общий storage boundary, включая сохранённые старые actions; non-task storage helpers не переопределяются.

После atomic target publication guard действует даже без source marker; держать отдельный долгоживущий lock/daemon или писать fence в старый journal не нужно. Старые непатченные binaries не умеют этот guard. Их последующий source append/tamper обнаруживается проверкой lineage и блокирует native continuation; абсолютная защита от произвольного старого binary не заявляется. Глобальная установка этой задачей не меняется.

## Приёмка

Public CLI проверяет preview без writes; valid apply/repeat; mixed chain/raw-byte preservation; stale rebind barrier; same-ID fresh rebind; variant semantic histories; divergent/corrupt sibling; source drift; target conflict; partial staging/atomic publish recovery; removed old worktree с доступными copied artifacts; packaged legacy write refusal. Native pending/publication fixtures должны блокировать apply без model/remote/1C calls. Go reader/history и helper historical resolver проверяют hashes, а current.json можно удалить без потери результата.
