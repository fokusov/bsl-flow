# task-estimation-skill

## Классификация

- Сложность: M
- Риск: medium

## Цель

Дать пользователю после финализации спеки изменения 1C консультативную оценку трудоёмкости в двух выражениях — человеко-часы полного цикла для мидл-разработчика с 3 годами опыта и агентные часы ИИ-исполнителя — вилкой минимум/максимум, с письменным артефактом рядом со спекой и машиночитаемым sidecar для последующей сверки план/факт. Оценка не является stage, gate или authorization контроллера.

## Текущее поведение

- `1c-spec` и `1c-spec-review` закрывают спеку (`final-validation.json`), после чего процесс переходит к реализации; трудоёмкость нигде не фиксируется.
- Классификация S/M/L и риск присутствуют в спеке, но не переводятся в часы; флаги запроса (`data_migration`, `form_flow`, `ambiguous_business_rule` и другие) не влияют ни на какую оценку.
- Controller journals фиксируют фактические попытки и wall time задач, но ни с каким планом не сопоставляются.
- Оценки, озвученные в чате, не сохраняются и теряются.

## Требуемое поведение

1. Новый assisted-скилл `1c-estimate` добавляется в семейство `1c-*` (исходник `global/skills/1c-estimate/`, установка вместе с остальными скиллами BSL Flow). Вход — OpenSpec change со спецификацией schema `bsl-flow`; managed-контракт `1c-task` не меняется: скилл читает и пишет только артефакты change и не вызывает контроллер.
2. Условие применимости: в change существует `spec.md`. Финальная оценка требует пройденной финальной валидации спеки: `final-validation.json` с пройденным вердиктом. Для S-change без обязательного ревью (ревью не требуется согласно классификации change) финальной валидацией считается завершённый lint: `lint-results.json` с `passed: true` в директории change. При отсутствии финальной валидации скилл отказывает с точной причиной; предварительные оценки не выдаются. Незакрытые BLOCK-находки (из `review-findings.json` в директории change) или material unknowns, влияющие на объём работ, делают финальную оценку невозможной: выдаётся отказ с точной причиной. Material unknown — неизвестное в спеке, которое влияет на объём, архитектуру, состав объектов метаданных или требует дополнительного согласования; примеры: неизвестный объём миграции данных, неопределённая интеграция, отсутствие требований к правам.
3. Артефакты оценки — `estimate.md` (human-readable отчёт) и `estimate.json` (sidecar) в директории change; это evidence-артефакты, а не schema-артефакты OpenSpec, и коммитятся вместе с change, как review sidecars. Финальный ответ скилла в чате обязан содержать обе итоговые вилки, уровень уверенности, главные драйверы вилки и путь к `estimate.md`.
4. Метод — декомпозиция: для `kind=estimate` спека разбивается на блоки работ по требованиям и критериям приёмки (объекты метаданных, модули/код, формы, права, интеграции/БСП, миграции данных, тесты, инструкция). Каждый блок получает собственные вилки human/ai-часов и краткое обоснование. Итог считается консервативной суммой: сумма минимумов и сумма максимумов по блокам. Оценка одним числом без декомпозиции запрещена; блок, чей объём нельзя оценить из спеки, переносится в `exclusions` с причиной. Для `kind=timebox` декомпозиция не требуется: блоки, суммы, exclusions и вилки не заполняются; записывается единственное значение `timebox_hours`.
5. Человеко-часы считаются по полному циклу для единственного baseline v1 `middle_3y`: анализ по спеке, реализация, самотестирование, исправления по код-ревью, краткая пользовательская инструкция. Состав фаз и их множители фиксируются в `estimate.md`.
6. ИИ-часы считаются как агентное wall-clock время: генерация, верификация, ремонты, ревью; ожидание ответов пользователя исключается. `estimate.json` фиксирует предполагаемые модель и effort: по умолчанию модель `bsl-flow-worker-default` и effort `medium`, заданные в references скилла, и вилку ожидаемого числа попыток.
7. Якоря: отправной точкой вилок являются встроенные якорные диапазоны S/M/L × low/medium/high риск, отдельно для human и ai. Итоговая вилка обязана сверяться с якорем: существенное расхождение объясняется в `estimate.md` явно. Существенное расхождение — отклонение любой границы итоговой вилки от соответствующей границы якорного диапазона более чем на 30%.
8. Допущения и уверенность: `estimate.md` обязан содержать перечень допущений, на которые опирается вилка, явные драйверы расширения вилки (включая применимые флаги запроса: `permissions`, `data_migration`, `data_deletion`, `posting`, `data_exchange`, `form_flow`, `external_artifact`, `ambiguous_business_rule`) и уровень уверенности `high|medium|low`. Material unknowns в спеке понижают уверенность до `low` и расширяют вилку либо приводят к отказу по правилу 2.
9. Спайки и исследовательские задачи без проверяемых критериев приёмки вилкой не оцениваются: выдаётся рекомендуемый timebox с `kind=timebox` и привязкой к хешам. Задача считается спайком, если в `spec.md` отсутствует раздел критериев приёмки, либо в change-метаданных указан `task_type=spike`, либо пользователь явно запросил timebox.
10. Свежесть: `estimate.json` хранит sha256 `spec.md` и, при наличии, `design.md` и `original-task.md`; для отсутствующих опциональных файлов соответствующее поле равно `null`, и при проверке staleness `null` равен только `null` (отсутствие файла не считается изменением). Также хранятся дата и время генерации. Изменение любого хеша (включая появление файла вместо `null`) делает оценку stale; скилл обязан перегенерировать её, а обнаруженная stale-оценка не может подаваться пользователю как актуальная. `estimate.md` обязан включать те же хеши, дату генерации и пометку об устаревании при несовпадении с текущими файлами.
11. Формат `estimate.json` — versioned closed schema (`schema_version: 1`): `change`, `created`, `kind=estimate|timebox`, `status=final`, хеши входов, `baseline`, `ai_basis` (модель, effort, вилка попыток), `blocks[]` (для `kind=estimate`), `totals` human/ai (для `kind=estimate`), `confidence`, `assumptions`, `fork_drivers`, `exclusions`, `timebox_hours` (для `kind=timebox`), опциональный `actuals`. `actuals` имеет минимальные зарезервированные поля: `human_hours`, `ai_hours`, `attempts`, `source`, `recorded_at`; в v1 они не заполняются автоматически. Точная JSON Schema публикуется в `references` скилла и валидируется детерминированной проверкой при генерации. В человеко-часах шаг округления 0.5 ч, в ИИ-часах 0.25 ч; псевдоточная дробность запрещена.
12. Сверка план/факт: `actuals` заполняется позже — агентные факт-часы и число попыток из controller journals (`.bsl-flow/tasks/<uuid>`), человеко-факт вручную пользователем. В v1 автосбор факт-часов и сводный отчёт дрейфа по проекту не входят: формат записи обязан их допускать, но не строит.

## Контекст 1С

- Конфигурация/подсистема: BSL Flow skills layer; метаданные 1С не изменяются. Предмет оценки — задачи разработки 1C, описанные спеками schema `bsl-flow`.
- Затрагиваемые механизмы: `global/skills/1c-estimate` (SKILL.md и references, включая JSON Schema и таблицу якорей), артефакты `estimate.md`/`estimate.json` в `openspec/changes/<change>/`.
- Evidence path: `spec.md` (+ `design.md`, `original-task.md`) → классификация S/M/L × риск → якорный диапазон → декомпозиция по требованиям и критериям (для estimate) → таблица блоков с вилками и драйверами → totals + confidence → `estimate.md`/`estimate.json` + итог в чате. 1С runtime не запускается; controller journals читаются только позже, при заполнении `actuals`.
- Якорные диапазоны и фазовые множители калибруются под специфику 1C (формы, БСП, права, миграции) и не претендуют на универсальность за пределами 1C-разработки.

## Не делать

- Не делать оценку обязательным stage/gate контроллера — отдельное будущее изменение.
- Не собирать факт-часы автоматически и не строить отчёт дрейфа/дашборд в v1.
- Не оценивать задачи без спеки «по описанию из чата».
- Не выдавать вилку для спайков — только timebox.
- Не вводить в v1 другие baseline-роли (junior/senior) и денежную оценку — только часы.
- Не выдавать итог без декомпозиции (для `kind=estimate`) и без сверки с якорем.
- Не отправлять спеку или оценку во внешние сервисы, кроме уже авторизованной модели сессии; не публиковать оценку отдельно от change.
- Не менять lifecycle, статусы и stage задач; не создавать `tasks.md`.
- Не считать ИИ-часы полным wall-clock, включающим ожидание пользователя.

## Критерии приёмки

- GIVEN change содержит `spec.md` и пройденный `final-validation.json` (или для S-change без обязательного ревью — `lint-results.json` с `passed: true`)
  WHEN выполняется `1c-estimate` для этого change
  THEN в директории change создаются `estimate.md` и `estimate.json` со `status=final`, а ответ в чате содержит обе итоговые вилки, уверенность, драйверы вилки и путь к `estimate.md`.
- GIVEN change не имеет пройденной финальной валидации
  WHEN запрашивается оценка
  THEN скилл отказывает с точной причиной; предварительная оценка не выдаётся.
- GIVEN спека содержит material unknowns либо незакрытые BLOCK-находки
  WHEN запрашивается финальная оценка
  THEN финальная вилка не выдаётся: скилл отказывает с точной причиной, перечисляя material unknowns и незакрытые BLOCK-находки.
- GIVEN оценка вида `kind=estimate` построена
  WHEN читается `estimate.md`
  THEN каждый блок работ имеет собственную вилку human/ai-часов с обоснованием, итог равен консервативной сумме блоков, а оценка одним числом без декомпозиции отсутствует.
- GIVEN `estimate.json` записан
  WHEN любой из хешированных входов (`spec.md`, `design.md`, `original-task.md`) изменяется или появляется/исчезает
  THEN оценка определяется как stale и не показывается пользователю как актуальная до перегенерации; `estimate.md` также содержит признак устаревания.
- GIVEN задача является спайком без проверяемых критериев приёмки
  WHEN запрашивается оценка
  THEN вилка не выдаётся; выдаётся рекомендуемый timebox с `kind=timebox` и `timebox_hours`, с той же привязкой к хешам.
- GIVEN оценка записана и задача завершена
  WHEN заполняется блок `actuals`
  THEN агентный факт (часы, число попыток) берётся из controller journals, человеко-факт вводится вручную, а исходные вилки плана не пересчитываются.
- GIVEN сгенерирован `estimate.json`
  WHEN выполняется детерминированная валидация по JSON Schema
  THEN документ проходит closed schema `schema_version: 1`, в человеко-часах выдержан шаг 0.5 ч, в ИИ-часах 0.25 ч; для `kind=timebox` отсутствуют `blocks[]` и `totals`, для `kind=estimate` присутствуют `blocks[]` и `totals`.

## Требуемые проверки

- [x] Static — JSON Schema `estimate-schema.json` прогоняется на эталонных валидных и негативных документах; SKILL.md и references скилла не содержат плейсхолдеров и описывают полный набор полей.
- [x] Unit — вычисление staleness по хешам входов (включая null-семантику), контроль шага округления вилок, проверка отсутствия декомпозиции для timebox.
- [x] Integration — полный прогон скилла на реальных изменениях `openspec/changes` (с `final-validation.json` и с `lint-results.json` для S-change без обязательного ревью), проверка артефактов и перехода в stale при изменении хеша спеки.
- [ ] UI — не требуется: собственного интерфейса нет.
- [ ] 1С runtime — не требуется: платформа 1С не запускается.

## Неопределённости / допущения

- Встроенные якорные диапазоны S/M/L × риск — стартовые величины из 1С-практики; точные числа фиксируются в references скилла и калибруются только накопленными `actuals`, авто-калибровка в v1 не входит.
- ИИ-часы сравнимы только вместе с зафиксированными моделью и усилием из `ai_basis`; автоматическое сопоставление разных моделей в v1 не выполняется.
- Человеко-факт зависит от дисциплины ручного ввода пользователем; без него сверка план/факт остаётся неполной по человеческой части.
- Managed-stage интеграция (обязательная оценка как этап контроллера) отложена в отдельную спецификацию; формат `estimate.json` допускает её без breaking change.
- Первые версии якорных диапазонов намеренно консервативны: уточнение возможно только после накопления завершённых задач с заполненными `actuals`.
