# self-learning-memory

## Классификация
- Сложность: L
- Риск: high

## Цель
Добавить в BSL Flow отдельный, управляемый механизм проектной памяти, который позволяет после сбоя продолжить задачу с последней доказанной точки, повторно применять подтверждённые полезные приёмы и учитывать прошлые ошибки без перечитывания всего проекта и без самовольного изменения нормативных правил.

## Текущее поведение
- Контроллер хранит журнал задачи, попытки и доказательства и умеет возобновлять зарегистрированную задачу.
- Контекст задачи и архитектурный bundle являются производными проекциями существующего состояния, а не новым источником истины.
- Нет отдельного журнала опыта, жизненного цикла знаний, контролируемого автоматического продвижения низкорисковых наблюдений и детерминированного подбора релевантной памяти для новой попытки.
- Текущий план архитектурного контекста реализуется отдельно; эта feature не меняет его этапы и использует только уже опубликованные контракты.

## Требуемое поведение
1. Feature должна храниться и развиваться как отдельный OpenSpec change `self-learning-memory`; её реализация не должна включаться в текущий план архитектурного контекста или менять его этапы.
2. Перед запуском или возобновлением попытки feature должна расширять существующую read-only проекцию `task context`/`Get-BFNext`, а не создавать параллельный контекст или state machine. Дельта feature: рабочий набор файлов/объектов, идентификаторы релевантных записей памяти и ID/hash сформированного bundle, привязанные к существующим `task_id`, `revision` и `attempt_id`. Получившаяся компактная Resume Capsule остаётся производной проекцией и не может разрешать действие, запрещённое журналом, gate или policy.
3. После сбоя feature должна потреблять решение существующего `Resume-BFAttempt` и его контрактов `side_effects`/`unresolved_effect`, не классифицируя эффект повторно. Память может добавить к разрешённому следующему attempt только релевантный bundle и рабочий набор; она не меняет disposition (`resume`, `retry`, `control-read`, `BLOCKED`) и не считает отсутствие receipt доказательством отсутствия эффекта.
4. Контроллер должен вести append-only Experience Ledger. В него попадают структурированные кандидаты, полученные из принятого результата, подтверждённой ошибки или успешного восстановления: область применимости, наблюдение, рекомендуемое/запрещённое действие, evidence references, fingerprints среды, счётчики подтверждений и противоречий. Сырые диалоги, chain-of-thought, секреты и произвольные дампы исходников хранить нельзя.
5. Запись памяти должна иметь явный жизненный цикл как минимум `candidate`, `shadow`, `accepted`, `quarantined`, `superseded`, `deprecated`. Каждая смена состояния должна быть отдельным событием с причиной и доказательством; история не перезаписывается.
6. `knowledge_class` является закрытым перечислением: `procedural`, `diagnostic`, `business_rule`, `authorization`, `test_or_waiver`, `architecture`, `controller_policy`, `model_routing`, `runtime_or_external_effect`; `risk_class` — закрытое перечисление `low`, `medium`, `high`. Автоматически продвигать можно только запись `procedural/low`, не расширяющую полномочия и не ослабляющую gates. Для `accepted` нужны не менее трёх согласованных подтверждений минимум из двух разных задач, отсутствие актуальных противоречий и совпадение обязательных fingerprints. Подтверждения согласованы, если у них совпадает canonical key из project ID, scope, recommended/avoid action и обязательных fingerprints. До продвижения кандидат применяется только в shadow/recommendation режиме.
7. Автопродвижение запрещено для всех `knowledge_class`, кроме `procedural`, и для `risk_class` `medium|high`. В частности, оно запрещено для бизнес-правил, прав и авторизации, ожидаемых результатов и waiver тестов, снижения риска, архитектурных решений, controller/skill/gate policy, model routing, runtime/native записей и публикации. Такие знания могут стать нормативными только через отдельное подтверждённое изменение существующего version-controlled источника.
8. Подбор памяти должен быть детерминированным и ограниченным: по стадии, типу задачи, затронутым путям/объектам, сигнатуре ошибки и fingerprints версий controller/schema/toolchain. Worker получает только сформированный bundle с ID записей и hash, привязанный к attempt; прямого доступа на запись в ledger у worker нет.
9. Противоречие, несовпадение обязательного fingerprint, изменение политики или опровергающее доказательство должны исключать запись из активного bundle и переводить её в quarantine/deprecated либо создавать superseding event. Контроллер должен уметь объяснить, почему запись выбрана, отклонена или продвинута.
10. Память по умолчанию локальна проекту и принадлежит контроллеру. Межпроектный обмен, облачная синхронизация и глобальное обучение не входят в эту feature.
11. Отсутствующая, пустая или повреждённая производная проекция памяти не должна делать старую задачу нечитаемой: индекс и Resume Capsule должны восстанавливаться из авторитетного журнала и append-only событий либо безопасно отключаться с явным blocker.

## Контекст 1С
- Конфигурация/подсистема: BSL Flow controller и CLI; метаданные конфигурации 1С не изменяются.
- Затрагиваемые объекты: task journal/attempts/evidence, task context, stage bundles, схемы controller-owned state, offline fixtures.
- Клиент/сервер: локальный controller; worker получает только read-only memory bundle.
- Расширение или основная конфигурация: не применимо.
- Существующие точки расширения/механизмы: `Resume`, task context, immutable journal, receipts, controller gates и stage prompts.
- Существенные ограничения: feature не даёт разрешения на реализацию или runtime; временное ограничение Unica сохраняется; память не является источником истины и не может обходить текущие gates.

Карта механизма: task journal + receipts + fingerprints → extractor опыта → append-only candidate events → shadow/validation/promotion policy → детерминированный memory bundle → Resume Capsule/stage attempt. Проверяемыми источниками являются journal, receipts, hashes, результаты тестов и принятые controller outcomes; текстовое утверждение worker само по себе доказательством не является.

## Не делать
- Не изменять и не дополнять `docs/ARCHITECTURE_CONTEXT_PLAN_RU.md` в рамках этой feature.
- Не создавать `tasks.md` и не превращать OpenSpec в оркестратор стадий.
- Не добавлять vector database, embeddings, graph service или внешний memory service до доказанной необходимости.
- Не давать модели права самостоятельно редактировать skills, controller policy, gates, AGENTS.md, ADR или бизнес-правила.
- Не хранить сырой transcript, chain-of-thought, секреты, персональные данные или полные копии проекта.
- Не переносить память между проектами и не объединять пользователей/репозитории.
- Не выполнять операции с базой 1С, native build/load/update или внешнюю публикацию для проверки этой feature.
- Не добавлять новую независимую state machine задачи: память должна потреблять существующее состояние controller.
- Не реализовывать повторно recovery-классификацию, `Get-BFNext`, `Resume-BFAttempt`, `side_effects` или `unresolved_effect`; feature только потребляет их опубликованный результат.
- Не рефакторить соседний код без прямой необходимости.

## Критерии приёмки
- GIVEN существующий план архитектурного контекста
  WHEN feature оформлена или реализуется
  THEN её change, код и проверки отделены, а hash и содержимое текущего плана не изменены.
- GIVEN существующие `task context`/`Get-BFNext` вернули подтверждённую стадию и `Resume-BFAttempt` разрешил продолжение retry-safe source-only попытки
  WHEN controller восстанавливается после сбоя
  THEN существующая проекция дополнена рабочим набором и memory bundle ID/hash, не меняя выбранный disposition и следующий разрешённый шаг.
- GIVEN `Resume-BFAttempt` вернул `control-read` или `BLOCKED` для неизвестного native/runtime либо внешнего эффекта
  WHEN feature добавляет память к Resume
  THEN disposition сохраняется, а запись не повторяется из-за рекомендации памяти.
- GIVEN принятый результат либо подтверждённая ошибка
  WHEN extractor формирует опыт
  THEN создаётся структурированный append-only candidate с evidence references и fingerprints, без секретов, transcript и chain-of-thought.
- GIVEN низкорисковый процедурный candidate
  WHEN порог подтверждений ещё не достигнут
  THEN запись используется только в shadow/recommendation режиме и не меняет поведение controller.
- GIVEN низкорисковый процедурный candidate с достаточными независимыми подтверждениями, совпадающими fingerprints и без противоречий
  WHEN promotion policy исполняется
  THEN создаётся отдельное событие `accepted`, причина продвижения объяснима и исходная история сохраняется.
- GIVEN candidate относится к бизнес-правилу, авторизации, waiver, gate, архитектуре или runtime/native записи
  WHEN promotion policy исполняется
  THEN автоматическое продвижение запрещено независимо от числа повторений.
- GIVEN accepted-запись получила актуальное противоречие или перестал совпадать обязательный fingerprint
  WHEN строится следующий bundle
  THEN запись не попадает в bundle, а журнал содержит quarantine/deprecation/superseding event с причиной.
- GIVEN несколько релевантных записей
  WHEN строится stage bundle
  THEN порядок и состав воспроизводимы на тех же входах, размер ограничен, а ID и hash bundle привязаны к attempt.
- GIVEN производный индекс удалён или повреждён, но авторитетные события целы
  WHEN controller выполняет восстановление
  THEN индекс перестраивается детерминированно; при невозможности безопасного восстановления возникает явный blocker без потери читаемости истории задачи.
- GIVEN старая задача без memory-событий
  WHEN её открывают или возобновляют после обновления
  THEN она остаётся читаемой и работает как задача с пустой памятью.

## Требуемые проверки
- [x] Static — закрытые/versioned schemas для событий, records, bundle и Capsule; запрет неизвестных полей там, где контракт controller-owned; проверка ссылок и canonical serialization/hash.
- [x] Unit — lifecycle и допустимые переходы; deduplication; порог promotion; запрет high-risk категорий; contradiction/quarantine; fingerprint invalidation; bounded deterministic retrieval; filtering секретов и запрещённого содержимого.
- [x] Integration — offline controller fixtures: accepted outcome → candidate → shadow → accepted → новый attempt получает bundle; crash/torn-event recovery; удалённый индекс; существующие dispositions source-only/native effect проходят без изменения; старая задача без памяти.
- [ ] UI — отдельного пользовательского UI в scope нет.
- [x] Smoke — существующие controller offline suites проходят при выключенной/пустой памяти, один end-to-end offline resume строит Capsule и продолжает с разрешённой точки.
- [x] Independent review — обязательный criticism-only review спецификации и design с reconciliation до реализации.

Runtime-проверки в базе 1С, native build/load и Computer Use для этой feature не требуются: проверяемый контракт относится к controller-owned локальному состоянию и offline fixtures.

## Неопределённости / допущения
- Точная физическая раскладка файлов и имена CLI-команд фиксируются design/реализацией, но не должны менять перечисленные контракты и границы полномочий.
- «Разные задачи» для порога promotion означают разные task IDs в одном проекте; повторные attempts одной задачи не считаются независимыми подтверждениями.
- Детерминированный replay используется только для проверки promotion policy и не засчитывается как production-подтверждение.
