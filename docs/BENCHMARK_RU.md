# Бенчмарк BSL Flow

Доказательная база для решения Ф6 (`docs/plans/2026-09-26-remediation-plan.md`): даёт ли
Core (скиллы + bootstrap) измеримое преимущество над «голым» агентом, и какой ценой по
времени/токенам. Результаты закрывают kill-list из Ф0.2 по правилам, зафиксированным
заранее в `bench/DECISION_RULES.md` — правила не меняются под результат.

Код и данные: `bench/`. Формат задач и как запускать — `bench/README.md`. Здесь — методика,
как читать агрегаты и ограничения.

## Методика

1. **Задачи.** Каждая задача (`bench/tasks/<id>/task.yaml`) — это формулировка «как от
   заказчика» (`original-task.md`), фикстура-конфигурация и скрытые от агента acceptance-
   проверки. Задачи размечены по размеру (S/M/L) и риску, отдельно помечены заведомо
   неоднозначные задачи, где правильный ответ агента — вопрос, а не догадка.
2. **Режимы.** `bare` (агент без скиллов/bootstrap BSL Flow), `core` (Core-скиллы
   установлены в изолированный конфиг), `managed` (пока не поддержан раннером — вне
   рамок текущего прогона).
3. **Раннер.** `bench/Invoke-BSLFlowBench.ps1` разворачивает фикстуру в чистом временном
   git-репозитории, запускает агента headless с промптом задачи, применяет таймаут, затем
   прогоняет скрытые acceptance-проверки тем же кодом, что использует продукт (грундинг,
   static-diff через BSL Language Server, YAxUnit — где есть runtime).
4. **Агрегация.** `bench/Measure-BenchResults.ps1` сворачивает JSON отдельных прогонов в
   `bench/results/<date>.json` и markdown-сводку: доля пройденных acceptance, доля ложных
   PASS, средний scope drift, время, токены/стоимость (только из usage хоста, никаких
   оценок на глаз), сравнение `bare` vs `core`.

## Главная метрика

**Доля ложных PASS** — агент заявил успех/PASS в финальном сообщении, а скрытые проверки
дали FAIL. Для 1С это важнее общей доли pass: ошибка, которую агент считает решённой,
дороже честного BLOCKED.

## Как запустить

Публичный офлайн-прогон (без платных вызовов, скриптованный fake-агент):

```powershell
pwsh -NoProfile -File bench/Invoke-BSLFlowBench.ps1 -Agent fake -Mode bare -Tasks 'bench/tasks/*' -Repeat 1 -OutputDir bench/results/run-fake
pwsh -NoProfile -File bench/Measure-BenchResults.ps1 -RunDir bench/results/run-fake -OutputDir bench/results
```

Прогон с реальным агентом (`claude` или `codex`) требует установленного CLI и, при
`-Mode core`, изолированной установки Core-скиллов; такой прогон запускает оператор
локально с явным разрешением. `.github/workflows/bench.yml` доступен только вручную, но
выполняет исключительно `fake`: в CI нет model-secrets, платных или сетевых агентских
вызовов.

## Приватная часть и приватность

Публичная часть бенчмарка идёт только на открытых фикстурах из `bench/fixtures/`.
Приватная часть — на клиентских проектах:

- запускается **только локально**, никогда не в CI этого репозитория;
- в репозиторий (и в этот документ) публикуются **только агрегаты** — доли, средние,
  без текста задач, кода клиента или путей из клиентского репозитория;
- перед публикацией агрегата проверяйте, что число задач в выборке достаточно велико,
  чтобы агрегат не идентифицировал конкретную задачу или клиента.

## Ограничения

- `yaxunit`-проверки требуют работающего runtime 1С и пропускаются в офлайн-прогонах
  (считаются в `skipped_runtime`, не засчитываются как pass или fail).
- `grounding`/`bslls_new_errors_max`/`static_diff` проверки допускают вердикт `NOT_RUN`,
  если соответствующий скрипт или BSL Language Server не установлен в среде прогона; это
  не засчитывается как FAIL, но снижает доверие к покрытию — см. поле `not_run_count`
  в агрегате.
- Офлайн `PASS` доказывает лишь контракт раннера и доступные статические/file-проверки.
  Он не доказывает поведение модели, стоимость, результат YAxUnit/Vanessa или runtime 1С.
- Стартовый набор (6 задач на `demo-mini`) — минимальный, не 20–30 задач из плана Ф6.2;
  расширение набора — отдельная работа, использующая тот же формат и тот же раннер.
- Метрики токенов/стоимости берутся из JSON-вывода агента (`claude -p --output-format json`
  / `codex exec --json`); при их отсутствии в выводе поле остаётся `null`, харнес не
  оценивает стоимость самостоятельно.
- Решения по kill-list принимаются только по правилам из `bench/DECISION_RULES.md`,
  зафиксированным до прогона.
