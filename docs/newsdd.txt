Да. Я бы как раз **не пытался дальше улучшать классический человеческий SDD**, а выделил в BSL Flow отдельный слой — условно **Agent-Native SDD**.

Сейчас большинство SDD-фреймворков всё ещё сохраняют человеческую модель: `requirements.md → design.md → tasks.md`. Даже Kiro работает именно так, хотя уже строит из `tasks.md` dependency graph и исполняет независимые задачи волнами. ([Kiro][1]) GitHub Spec Kit идёт дальше в формулировке идеи: спецификация должна стать **executable artifact**, а после implementation нужен convergence-loop `implementation ↔ spec ↔ plan ↔ tasks`. ([GitHub][2])

Но я думаю, для BSL Flow можно сделать следующий шаг.

## Что сейчас не так со спеками для агентов

Типичная спека:

```markdown
### 3. Реализовать обработку документа

Добавить проверку заполнения склада.
Использовать существующий механизм контроля остатков.
Не менять типовую конфигурацию.

Acceptance:
- документ проводится;
- при отсутствии склада возникает ошибка;
- существующая логика не ломается.
```

Человеку нормально.

Для агента тут куча скрытой работы:

* что именно менять;
* где искать существующий механизм;
* какие файлы разрешено менять;
* что означает «существующая логика не ломается»;
* как доказать выполнение acceptance;
* можно ли менять публичный интерфейс;
* что выполнить сначала;
* от каких задач зависит эта;
* когда остановиться и спросить человека.

То есть задача агента сейчас примерно:

> прочитать prose → восстановить intention → придумать DAG → определить scope → придумать проверки → реализовать → самому решить, что готово.

Это довольно дорогая и недетерминированная часть работы.

# Я бы поменял центральную сущность BSL Flow

Не:

> **Spec → Plan → Tasks → Code**

а:

> **Intent → Contract → Execution Graph → Evidence**

Где Markdown остаётся, но перестаёт быть главным исполняемым артефактом.

### 1. Intent — человеческий слой

Короткий `spec.md`:

```markdown
# Проверка склада при проведении заказа

## Goal

Не позволять проводить заказ без заполненного склада.

## Why

Сейчас документы без склада попадают в обмен и вызывают ошибки.

## Constraints

- типовую конфигурацию не изменять;
- существующие механизмы проверки использовать повторно;
- изменение должно быть минимальным.
```

Это очень удобно читать человеку.

---

### 2. Contract — что должно быть истинно

Например:

```yaml
requirements:

  - id: R1
    when: "проводится ЗаказКлиента"
    if: "Склад не заполнен"
    then:
      - "проведение запрещено"
      - "пользователь получает понятное сообщение"

  - id: R2
    when: "Склад заполнен"
    then:
      - "текущее поведение проведения сохраняется"

constraints:
  configuration_changes: forbidden
  extension_only: true
  public_api_changes: forbidden
```

Это уже близко к EARS, который использует Kiro для структурированных требований. Такой формат специально снижает неоднозначность требований. ([Kiro][1])

Причём человеку YAML вообще необязательно читать.

---

# 3. Самое важное — Execution Graph

Вот здесь я вижу настоящую эволюцию BSL Flow.

Не `tasks.md`:

```markdown
- [ ] Найти обработчик
- [ ] Добавить проверку
- [ ] Написать тесты
```

А что-то вроде:

```yaml
tasks:

  - id: T1
    kind: explore

    goal: >
      Найти существующий механизм проверки заполнения
      склада при проведении документов.

    outputs:
      - existing_mechanism
      - candidate_extension_point

    evidence:
      - source_location
      - short_reasoning

    mutation: forbidden


  - id: T2
    kind: implement

    depends_on:
      - T1

    goal: >
      Добавить минимальную проверку склада
      через найденную точку расширения.

    allowed_scope:
      - extensions/**

    forbidden:
      - configuration/**
      - public_api_changes

    satisfies:
      - R1
      - R2

    verify:
      - V1
      - V2


  - id: T3
    kind: review

    depends_on:
      - T2

    checks:
      - minimal_change
      - no_duplicate_logic
      - regression_risk
      - requirement_coverage
```

Это уже не список задач.

Это **program for agents**.

Именно это я бы сделал центральным артефактом BSL Flow.

# 4. Verification тоже должна быть исполняемой

Вот здесь большинство SDD пока слабоваты.

Не:

```markdown
Acceptance criteria:

- всё работает;
- ошибки нет;
- регрессий нет.
```

а:

```yaml
verification:

  - id: V1
    requirement: R1
    type: scenario

    arrange:
      document: ЗаказКлиента
      warehouse: null

    act:
      operation: Провести

    expect:
      conducted: false
      message_contains: "склад"


  - id: V2
    requirement: R2
    type: regression

    arrange:
      document: ЗаказКлиента
      warehouse: valid

    act:
      operation: Провести

    expect:
      conducted: true
```

А дальше executor уже решает, чем это проверить:

* Vanessa Automation;
* xUnitFor1C;
* EDT;
* BSL LS;
* временная база;
* MCP к 1С;
* специальный smoke runner.

То есть:

**requirement → verification → evidence**

становятся трассируемыми.

Это значительно важнее красивого `design.md`.

# Ещё одно важное изменение: задача должна иметь `Definition of Done`

Например:

```yaml
done_when:

  requirements:
    - R1
    - R2

  verification:
    must_pass:
      - V1
      - V2

  quality:
    syntax_errors: 0
    critical_review_findings: 0

  evidence_required:
    - changed_files
    - verification_results
    - implementation_summary
```

Теперь агент **не решает самостоятельно**, когда задача закончена.

Executor может программно сказать:

```text
T2 status: BLOCKED

Reason:
V2 has no evidence.
```

или:

```text
T2 status: DONE

Satisfied:
R1 ✓
R2 ✓
V1 ✓
V2 ✓
```

Это уже качественно другой уровень автономности.

# И появляется очень полезный тип задачи: `explore`

Мне кажется, для разработки 1С он вообще критичен.

Агенты часто делают ошибку:

> «Мне надо изменить поведение → сейчас напишу код».

Хотя правильная последовательность:

```text
explore
   ↓
understand
   ↓
choose extension point
   ↓
implement
   ↓
verify
```

Поэтому execution graph может содержать разные `kind`:

```text
explore
research
design
implement
migrate
test
review
fix
document
```

И для каждого вида будут разные права.

Например:

```yaml
kind: explore
mutation: forbidden
```

или:

```yaml
kind: review
mutation: forbidden
```

Это особенно хорошо ложится на твою мультиагентную архитектуру.

# Тогда оркестратор получает настоящий DAG

Допустим:

```text
             ┌─ T2 implement server ─ T4 test ─┐
T1 explore ──┤                                ├─ T6 review
             └─ T3 implement UI ───── T5 test ─┘
```

Оркестратор сразу видит:

```yaml
T1:
  model: Luna
  parallel: false

T2:
  depends_on: [T1]

T3:
  depends_on: [T1]

T4:
  depends_on: [T2]

T5:
  depends_on: [T3]

T6:
  depends_on: [T4, T5]
```

И уже может выбирать:

```text
explore          → DeepSeek Flash
small implement  → DeepSeek Flash
complex design   → Sol
review           → другая модель
1C architecture  → Sol/Astra
```

Kiro уже делает похожую вещь: анализирует зависимости между задачами и исполняет независимые задачи параллельно волнами. ([Kiro][1])

Но я бы в BSL Flow **не заставлял модель каждый раз выводить dependency graph из Markdown**.

Мы уже знаем его.

Давайте просто сохраним его.

# Причём design.md я бы сделал необязательным

Это ещё одна вещь, которую я бы поменял.

Сейчас SDD часто заставляет делать:

```text
requirements
    ↓
design
    ↓
plan
    ↓
tasks
```

Даже когда задача:

> Добавить одно условие в существующий обработчик.

Получается тот самый overengineering, против которого ты уже боролся в BSL Flow.

Я бы ввёл `complexity-driven artifacts`.

Например:

```yaml
complexity: trivial
```

даёт:

```text
intent
execution
verification
```

А:

```yaml
complexity: medium
```

даёт:

```text
intent
contract
execution
verification
```

И только:

```yaml
complexity: high
architecture_change: true
```

даёт:

```text
intent
requirements
design
ADRs
execution graph
verification
```

Это существенно уменьшит стоимость работы агентов.

# Markdown при этом выбрасывать не надо

И это принципиально.

OpenSpec сейчас сознательно остаётся на обычном Markdown: proposal, requirements/scenarios, design и task checklist — именно чтобы формат оставался простым для человека и переносимым между десятками AI-агентов. ([GitHub][3])

Я бы не делал BSL Flow чистым JSON/YAML framework.

Лучше:

```text
Human layer
    ↓
Markdown

Agent contract layer
    ↓
structured YAML

Runtime layer
    ↓
JSON / JSONL
```

Получается хороший separation of concerns.

# И здесь возникает ещё одна интересная идея

Сейчас мы говорим:

> агент реализует спецификацию.

Я бы сформулировал иначе:

> **агент обязан предоставить доказательства выполнения контракта.**

То есть задача агента не:

```text
write code
```

а:

```text
make R1…Rn true
and produce evidence V1…Vn
without violating C1…Cn
```

Это очень близко к constraint solving:

```text
Goal:
R1 ∧ R2 ∧ R3

Subject to:
C1 ∧ C2 ∧ C3

Proof:
V1 ∧ V2 ∧ V3
```

И вот такой формат LLM/агентам гораздо естественнее исполнять, чем 800 строк `design.md`.

## Что я бы сделал в BSL Flow

Не стал бы сейчас менять весь framework.

Я бы сделал **экспериментальный `execution-contract v0.1`** рядом с существующим SDD:

```text
spec.md
        ↓
spec-review
        ↓
compiler
        ↓
execution.yaml
        ↓
executor
        ↓
agents
        ↓
evidence
        ↓
convergence
```

То есть текущая хорошая человеческая спека остаётся.

Но перед реализацией BSL Flow **компилирует её в агентный формат**.

Это даёт нам очень хороший эксперимент: взять 20 реальных задач, которые ты уже прогонял через BSL Flow, и сравнить:

```text
Markdown SDD
vs
Agent Execution Contract
```

по твоим же метрикам:

* successful completion;
* количество перепланирований;
* количество уточнений;
* количество лишних изменений;
* regression rate;
* reviewer findings;
* tokens;
* duration;
* **cost per accepted task**.

И вот это, на мой взгляд, может оказаться **одной из самых сильных идей следующей версии BSL Flow**: не очередной SDD framework, а **компилятор человеческого intent в исполнимый контракт для coding agents**.

Причём для 1С это особенно интересно: environment довольно строгий, сущности хорошо формализуются, а проверки можно постепенно превращать в реальные executable verifiers.
