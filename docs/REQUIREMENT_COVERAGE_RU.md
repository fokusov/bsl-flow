# Достаточность приёмки

Контроллер отличает успешный тест от достаточного покрытия задачи. Доверенный request задаёт требования и связь с критериями; независимый reviewer проверяет, способны ли конкретные тесты подтвердить каждое требование. Исполнитель не может изменить этот контракт.

```json
"requirements": [
  {
    "id": "negative-input",
    "text": "Отрицательное значение вызывает ожидаемое исключение; нужен исполненный отрицательный тест.",
    "criterion_ids": ["unit-tests"]
  }
]
```

Все критерии должны быть связаны хотя бы с одним требованием. Для исполняемых проверок нужны `protected_paths` с независимыми тестами и fixtures. Новая native-задача не регистрируется без `requirements`. Ранее зарегистрированные задачи остаются читаемыми: покрытие не добавляется задним числом. Для остальных новых задач поле включается явно.

Наличие `requirements` делает `code_review` обязательным даже для S/low. Reviewer возвращает отдельный `coverage_review`: ровно одну оценку каждого требования, ссылки на объявленные критерии, точные test IDs, существующие защищённые файлы и объяснение проверяемого поведения. Один тест может обслуживать несколько требований; общий набор ссылок должен охватывать все объявленные тесты. Контроллер сам вычисляет хеши файлов и сохраняет `coverage-review-binding.json`.

Review выполняется до verify: он оценивает способность теста наблюдать требуемое поведение при будущем исполнении. `SUFFICIENT` не утверждает, что тест уже прошёл. Следующий этап обязан выполнить критерий и проверить оригинальный результат. Общий JUnit-адаптер сопоставляет `expected_tests` с `testcase.name`; native 1С-адаптер использует `classname.name`. Выбирай ID по фактическому формату отчёта соответствующего адаптера.

`INSUFFICIENT` останавливает задачу с `BLOCKED`. Обычное согласование замечаний к коду не может превратить недостаточное покрытие в PASS. Требуется доверенный пересмотр требований или тестового контракта. Например, проверка наличия функции в исходнике не подтверждает требование об исполнении отрицательного теста.

Перед verify и acceptance контроллер повторно проверяет свежесть независимого review, его исходный результат и binding. Изменение требований, критериев, тестов или исходников инвалидирует прежнюю приёмку. Отсутствующий binding не создаётся на этапе acceptance.

Для проведения нужны наблюдения о движениях и отказах; для обмена — о сопоставлении и повторной обработке; для прав — о разрешённом и запрещённом сценарии. Эти ожидания задаются конкретной задачей. Фреймворк не придумывает бизнес-правила и не выдаёт один unit-пилот за проверенный корпус всех конфигураций 1С.

Проверка структуры и свежести детерминирована. Оценка смысловой достаточности остаётся суждением независимого reviewer и может ошибаться; поэтому сохраняются его объяснения, реальные исходники тестов и первоначальные требования. Это проверяемая граница приёмки, а не математическое доказательство полноты бизнес-тестов.
