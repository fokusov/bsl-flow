## Inventory and temporary settings

The registered `execution_profile.codex_skills_sha256` is `Get-BFHash` of the array sorted by absolute `path` (case-sensitive), with each record containing exactly `name`, `path`, `scope`, `enabled`, and `sha256` of `SKILL.md`. Store neither descriptions nor skill contents in the projected inventory. On disk the managed receipt wraps that array in `{skills:[...]}`. Baseline and post-execution inventories must equal the registered hash. The disabled inventory must equal the baseline with only `enabled=false` changed. Cached reuse also verifies the original skill bytes.

The pinned app-server request is `skills/list` with `{cwds:[worker],forceReload:true}` after `initialize` and `initialized`. The shipped RPC helper uses PowerShell/.NET only, bounded stdout/stderr, a deadline, cancellation, and exact owned-process termination. It permits only read-only inventory/config methods. No Python installation is required.

Retain the real `CODEX_HOME` and the default existing SQLite state. **Do not redirect `sqlite_home` to an empty directory**: that earlier experiment caused initialization delays/timeouts. Do not redirect `CODEX_HOME`, copy authentication, or alter global config. Codex home owns authentication, SQLite state, `.sandbox`, `.sandbox-bin`, `.sandbox-secrets`, and sandbox setup state. A different home changes the security runtime as well as configuration discovery.

Worker execution uses `exec --ignore-user-config --ignore-rules --ephemeral --skip-git-repo-check`, selected model/effort, approval policy `never`, the named managed filesystem profile, and temporary argv overrides. Plugins, multi-agent, memories, shell snapshot, hooks, browser/computer use, and automatic skill MCP dependency installation are disabled. `skills.include_instructions=false` suppresses catalog injection; it alone is not a skill enforcement boundary. App-server inventory uses explicit MCP configuration overrides and never dispatches a model turn.

`mcp_servers={}` alone does not clear inherited tables in app-server configuration. The adapter first reads configuration without starting MCP transports and retains server names only. It disables each known server with a bare CLI key, guards subsequent inventory calls with exact names/enablement, and checks again before dispatch. Only `[A-Za-z0-9_-]+` names are accepted: quoted dotted keys became literal names in the pinned parser. Unica whole-table registration precedes the final per-name denials. The worker ignores user configuration and receives no partial disabled global definitions. These observations detect configuration drift but do not lock concurrent global edits.

RPC cleanup preserves the primary exception while still attempting owned-process termination and disposal after a broken stdin pipe. Malformed phase-3 MCP responses produce only parser error identity, exception type, line hash/length and available JSON coordinates. Configuration bodies and exception messages are not persisted.

Controller records reside under the read-denied project `.bsl-flow/tasks`. Provider configuration and writable scratch reside separately under `.bsl-flow/hosts/<task>/<attempt-hash>`: a Windows deny on an ancestor cannot be reopened for its child. Source is writable only for `implement`; dependency snapshots/configuration remain read-only. A filesystem observation preflight must succeed before the worker request.

## Unica

Unica is registered explicitly from the pinned public bootstrap with `run --plugin-root <root>`, and `enabled_tools` equals the raw `unica.allowed_tools` array. The MCP child command is another pinned `codex sandbox` with the same filesystem permissions; the outer Codex process must not launch an unsandboxed bootstrap. The verified runtime tree is read-only; only the bootstrap `.locks` directory is writable. No internal Unica adapters or runtime jobs are allowed.

The adapter compares native `mcpServerStatus/list` tool identities with the exact allowlist before model dispatch. cc requires an empty MCP inventory. Unknown/extra/missing tools or pagination block dispatch. This route still needs a successful native Codex synthetic MCP smoke. The independently measured OpenCode route is documented separately in `unica-bridge-contract.md` and does not prove Codex behavior.
