# BSL Flow 0.8: автономное выполнение и единый CLI

Дата: 2026-09-10. Статус: реализация продолжается; этапы C–E интегрированы, этап F принят на локальном FILE remote; локальные проверки G завершены, полный чистый CI выполняется при push. Этот документ продолжает первоначальный план M0–M8, сохраняя его незавершённые проверки. Их история приведена в [VERIFICATION.md](../VERIFICATION.md).

## Цель и граница готовности

Пользователь задаёт доработку 1С и отвечает на существенные бизнес-вопросы. Контроллер самостоятельно выполняет применимые этапы, исправляет обнаруженные ошибки в заданных пределах и передаёт проверенный результат. Проверки относятся к конкретным требованиям, исходникам, тестам, базе и артефакту. Прерывание не приводит к повторной записи с неизвестным результатом.

Первый подтверждаемый контур: Windows, последовательная задача, Git worktree, Codex worker, существующий независимый reviewer, одна явно разрешённая файловая тестовая база, разработка через расширение. Поддержка UI/EPF, параллельных баз и других worker providers расширяется только после соответствующих пилотов. Release readiness определяется таблицей gates, а не наличием кода.

## Архитектурное решение: собственный бинарный CLI

Строгий CLI уже реализован в `Invoke-BSLFlowTask.ps1`: закрытый набор команд, JSON envelope, конечные коды и детерминированные transitions. Инструкции этапов находятся в skills; worker возвращает предложения, controller проверяет evidence и единолично принимает результат.

В 0.8 вводится `bsl-flow.exe` как стабильный пользовательский вход. Он содержит версионируемый bundle инструкций и controller, проверяет его целостность и вызывает фиксированный entrypoint. Авторитетный PowerShell 7 engine сохраняется и запускается через стандартную машинную установку `C:\Program Files\PowerShell\7\pwsh.exe`; fallback на Windows PowerShell 5.1 не предусмотрен. Бинарник не ведёт вторую историю, не интерпретирует PASS самостоятельно и не обходит authorization. Требования Git и worker provider остаются явными.

Сравнение вариантов:

| Вариант | Польза и цена | Решение |
| --- | --- | --- |
| Только существующий PowerShell CLI | Минимум изменений; многословный запуск и отдельная поставка файлов | Сохраняется для совместимости и диагностики |
| Компилируемый CLI + существующий engine | Один вход, embedded bundle, строгий argv; повторно используется проверенное хранение и recovery | Выбран для первого increment |
| Полный перенос engine на Go | Повторная реализация критических контрактов; потребуется миграция state и повторная приёмка | Отложен до доказанного ограничения текущего engine |

По явному выбору пользователя бинарный host пишется на Go, со стандартной библиотекой и embedded bundle. Пользователь устанавливает Go toolchain; глобальные установки SDK фреймворк не выполняет. Первый проверяемый runtime — Windows с существующим PowerShell 7 engine в стандартном машинном пути. Новая сборка host входит в identity исполняемой поставки. Различия оболочек, UTF-8, quoting, path traversal, неполная распаковка, подмена bundle и exit propagation проверяются отдельно. Rust/.NET host не входят в решение.

Само размещение текста внутри exe не является enforcement. Граница остаётся прежней: worker sandbox, недоступное ему authoritative state, проверяемые данные и controller-owned actions. Действия администратора вне managed-контура не контролируются этим механизмом.

## Порядок реализации

### A. Публичный CLI и воспроизводимая поставка

Команды `version`, `help`, `task start/status/next/run/update/resume/cancel/record/accept` отображаются на существующие действия. Неизвестные/повторные аргументы отклоняются. JSON и exit codes сохраняются. Embedded bundle исполняется из стабильного каталога своей версии; неожиданные или изменённые файлы блокируют запуск. Инструкции остаются читаемыми и изменяемыми в исходном репозитории, обновляются сборкой.

Приёмка: сборка из чистого checkout, CLI parity, реальная регистрация/status/cancel в отдельном Git fixture, кириллица и пробелы, отсутствие shell injection, tamper rejection и полная offline regression engine. Наличие exe не закрывает runtime 1С gate.

### B. Ограниченный цикл диагностики и исправления

Добавить opt-in request policy для числа исправлений проверяемых source-only ошибок. Прежние requests сохраняют остановку при ошибке. Диагностика читает точный исходный отчёт и предлагает исправление либо объясняет необходимость бизнес-уточнения/ремонта среды. Только controller допускает следующий implement. Изменение исходников инвалидирует применимые code review/verification, после исправления выполняется свежая проверка.

Автоматическое исправление допускается после доказанного завершения проверки без изменения исходников и неопределённых внешних эффектов. Пропавший отчёт, timeout, ошибка протокола, подмена исходников, неизвестный результат runtime операции и неподтверждённая база остаются BLOCKED. Модель не может разрешить себе повтор записи. Повторяющаяся ошибка без изменения исходников или исчерпание бюджета завершает цикл. Текст диагностики не может менять критерии или authorization.

Приёмка: failure→diagnosis→fix→fresh review/verify→acceptance; бюджет исчерпан; диагностика требует ответа; source tampering; stale/отсутствующий JUnit; прерывание и запрет повторной записи; сохранение истории исходной ошибки. Текущие проверки выполняются в PowerShell 7; ранее проведённые проверки в PS5.1/7 сохраняются только как историческое evidence. Отдельно учитывается один реальный worker pilot.

### C. Контракт runtime и воспроизводимая тестовая среда

Переиспользовать preflight/result helpers из `1c-verify` и readiness inventory из `1c-init-project`. Установленный публичный Unica API предварительно исследуется через разрешённый read-only/preview route. Нельзя реконструировать его аргументы по устаревшим docs или подменять наблюдаемый target полями запроса.

Предварительно выбран пользователем `C:\BASES\DEMO\bp1` (Бухгалтерия). Секреты не входят в этот документ, project config, Git, отчёты или bundle. До применения требуется конкретный просмотренный план операций: workspace/source set, платформа, тестовое расширение, база, отчёты, ожидаемые эффекты и восстановление. Временное ограничение Unica сохраняется; объявление новой версии provider не снимает его.

Runtime adapter должен разделять preview, допуск операции, исполнение и запись результатов. Нужны identity попытки, захват единственного доступа к базе, фактический состав/версия цели, выбранные тесты, исходники и SHA-256 артефакта. Только оригинальный свежий результат завершённой операции может закрыть gate. Preview никогда не даёт PASS бизнес-проверки.

Пилот уточнил обязательную проверку готовности: запись расширения с `active=true` и успешный update не доказывают его применение в сеансе. Нужно обнаруживать отказ применения, включая конфликт внутренних UUID, и сопоставлять ожидаемый набор тестов с фактически обнаруженным. Проверка UUID охватывает собственные внутренние идентификаторы, а не только атрибуты `uuid` объектов; шаблонные значения scaffold не должны попадать в загрузку.

Изолированная база/контролируемое восстановление, повторяемые fixtures и ограничение фоновых/внешних эффектов определяются для выбранного пилота. После потери ответа выполняется контрольное чтение состояния; сборка, загрузка или бизнес-запись автоматически не повторяются. EPF/ERF требуют отдельных build/roundtrip/open/behavior gates; API загрузки CF/CFE не считается загрузчиком EPF.

Приёмка первого контура C5 выполнена на явно разрешённой FILE-базе `C:\BASES\DEMO\bp1`: публичный controller провёл BSLFlowPilot через load/update, контрольное чтение после ошибки пути отчёта, продолжение только тестов, original JUnit 5/5 PASS и acceptance. Managed adapter принимает только строгий `native_1c` criterion, связывает target, платформу, snapshot исходников, ожидаемые test IDs и сохраняет pending/recovery evidence. Это доказательство одного FILE/extension/YAxUnit маршрута. Оно не подтверждает произвольные конфигурации 1С, server-base, UI, EPF/ERF, production rollback или бизнес-операции вне пилота. Подробности и receipt IDs — в [NATIVE_RUNTIME_RU.md](NATIVE_RUNTIME_RU.md).

### D. Критерии, тесты и бизнес-уточнения

Построить явную связь требование→наблюдение→тест→evidence. Сохранить trusted input channel для первоначальных требований и решений пользователя. Предложения критериев и тестов проверяются независимо от implement; изменение ожидаемого результата требует нового рассмотрения требований и инвалидирует старую приёмку.

Готовые 1С skills используются для написания тестов. Проверяется достаточность бизнес-наблюдений: для проведения — движения/отрицательные случаи, для обмена — соответствие и повторная обработка, для прав — разрешённый и запрещённый сценарии. Название типа проверки само по себе не доказывает покрытие.

Контракт `requirements` и независимый `coverage_review` интегрирован. Требования связываются с criterion IDs, test IDs и защищёнными исходниками; controller проверяет полный замкнутый schema и вычисляет собственную hash-binding. `INSUFFICIENT` блокирует verify, а изменение scope инвалидирует прежнюю достаточность и acceptance. В D2 реальный model-пилот доказал обнаружение слабого теста, исправление test contract и JUnit 2/2; отдельный более ранний native BSLFlowPilot подтвердил 5/5 тестов контроллера C и не проверял новый coverage gate D. Эти два пилота не являются бизнес-корпусом проведения, обмена, прав, UI или EPF. Подробности — в [REQUIREMENT_COVERAGE_RU.md](REQUIREMENT_COVERAGE_RU.md).

### E. Фоновый исполнитель

Добавить один локальный supervisor с явным списком проектов/задач. Он вызывает тот же controller, не создаёт свою машину состояний и не изменяет receipts. Только задачи с заранее разрешённым продолжением запускаются автоматически. Вопрос, неопределённый эффект и исчерпание бюджета останавливают dispatch; ответ/разрешённое восстановление позволяют продолжить.

Нужны один владелец запуска, сохранённый operational status, возобновление после перезапуска и уведомления только о содержательных событиях. Регистрация службы/планировщика на компьютере — отдельное явное действие. Не создавать скрытую системную автозагрузку в installer.

Durable runner читает полный `events.jsonl` до цикла, отклоняет malformed/torn строки, использует все event keys для дедупликации независимо от cache-256 и очереди и восстанавливает `execution_error` без повторного dispatch. Quiet-состояния `needs_input`, `blocked`, `cancelled` и `completed` получают ровно одно durable `observed` событие. Межпроцессный owner lock освобождается после нормального выхода. Эти инварианты подтверждены 20 regression checks в PowerShell 7. Долговременная unattended эксплуатация и регистрация службы остаются отдельными операционными проверками.

### F. Управляемая поставка

Acceptance остаётся отдельной границей от публикации. Delivery использует точные принятые исходники/артефакт, декларацию разрешённых действий и отдельный журнал попыток. Начать с локального handoff: описание изменения, manifest, результаты проверок, готовый patch/артефакт. Commit/PR/push и установка в среду включаются только в заранее разрешённом scope.

Нельзя получить delivery PASS из старого acceptance после изменения исходников. Повтор публикации после неизвестного ответа требует проверки удалённого результата. Production rollout и rollback определяются отдельно для конкретной среды.

Приёмка: локальный handoff полностью соответствует принятому manifest; повтор идемпотентен; stale acceptance блокируется; публикация без соответствующего разрешения не выполняется.

### G. Проверки и выпуск

Сохранить offline suite и разделить её с host/model/runtime pilots. Добавить CI offline suite без секретов и платных вызовов. Выпускать dev-артефакты с точным статусом A–G; стабильную автономную 1С версию объявлять только после реального сквозного сценария.

Корпус развивается от одной небольшой доработки расширения к проведению, обмену, правам, форме и внешней обработке. Измерять принятие результата, существенные вмешательства, исправления, время и доступный фактический usage. Не выводить качество модели или стоимость всего процесса из одного успешного fixture.

## Зависимости и проверки решений

A и B могут разрабатываться параллельно с read-only исследованием C. Applied C начинается после точного разрешения и проверенного preflight. D использует контракты B/C. E переиспользует recovery controller и не снимает его blockers. F зависит от подтверждённого acceptance. G сопровождает каждый increment.

Независимый review обязателен для новых переходов, восстановления и границы host/bundle; findings рассматриваются по фактическим сценариям. Основной агент проверяет совместное поведение. Успех субагента и наличие кода не заменяют приёмку.

## Что не входит в первый подтверждённый контур

Распределённая очередь, web-панель, автоматический выбор моделей по непроверенной экономии, перенос всей state machine на другой язык и одновременная запись нескольких задач в одну базу. Потребность в них оценивается по реальным выполненным задачам.
