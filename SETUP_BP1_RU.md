# Первое безопасное подключение YAxUnit и Vanessa Automation к демо-БП 3

В BSL Flow v0.6.1 готовые локальные заготовки создаёт [генератор навыка](global/skills/1c-verify/references/test-starters.md), а проверку выбранного маршрута и сохранение результатов описывает [контракт доказательств](global/skills/1c-verify/references/test-evidence.md). Сначала проверь один тест. Успешная генерация файлов или preview не означают, что движок установлен, TestClient подключён или тест прошёл. На явно разрешённой `bp1` интерактивно прошли один тест YAxUnit и один локальный сценарий Vanessa; свежий JUnit и TestClient этим не доказаны. См. [VERIFICATION.md](VERIFICATION.md).

> Назначение этого документа — провести первый, **контролируемый** запуск тестового окружения для человека, который раньше не работал ни с YAxUnit, ни с Vanessa Automation. Это инструкция-план: она не устанавливает расширения и не запускает базу сама по себе.

## 1. Граница работ и исходное состояние

В примерах ниже целевая учебная база — файловая база 1С по условному пути `C:\BASES\DEMO\bp1`. Подставь путь к своей разрешённой тестовой копии. Это **физическая информационная база**, а не каталог проекта исходного кода.

Внутри `bp1` есть старый `_cfe_src`, не относящийся к этой задаче. Его не используем как место для тестов, не удаляем и не переименовываем.

Проверено только наличие файлов на диске:

| Что | Путь | Состояние |
|---|---|---|
| Движок модульных тестов | `C:\YAxUnit\YAxUnit-25.12.cfe` | найден |
| Расширение дымовых тестов | `C:\YAxUnit\Smoke-25.12.cfe` | найден |
| Обработка BDD-тестирования | `C:\vanessa-automation\vanessa-automation.epf` | найдена |
| Расширение VA | `C:\vanessa-automation\VAExtension.1.29.cfe` | найдено |
| Расширение MCP-клиента | `C:\vanessa-automation\client_mcp.cfe` | найдено |

Не проверено и не следует предполагать:

- есть ли уже какие-либо из этих расширений в `bp1`, их внутренние имена и версии;
- совместимы ли именно эти версии с платформой и релизом данной БП;
- кто имеет права администратора базы и доступ к Конфигуратору;
- есть ли в базе активные пользователи, фоновые задания, обмены или тестовые данные;
- какие именно команды и роли будут видны в интерфейсе БП.

Поэтому правило первого запуска: **сначала инвентаризация, затем точечная установка только отсутствующего компонента**. Нельзя «на всякий случай» загружать все `.cfe`, обновлять существующие расширения, удалять расширения или выполнять массовое изменение свойств.

## 2. Что для чего нужно

- **YAxUnit** — тестовый движок для программных (модульных) тестов. Он нужен, когда проверяем отдельную бизнес-логику BSL без ручного прохождения формы.
- **Smoke** — дополнительный набор дымовых проверок для YAxUnit. В первый день он не обязателен: без собственных тестов он не доказывает работоспособность доработок и может дать большой, нецелевой прогон.
- **Vanessa Automation (EPF)** — внешняя обработка для сценариев поведения в интерфейсе 1С (feature-файлы).
- **VAExtension** — отдельное расширение для возможностей Vanessa, которые требуются не во всех профилях. Его необходимость определяет конкретный профиль тестов/документация используемой версии VA; не устанавливай его только из-за имени файла.
- **client_mcp** — расширение для выбранного MCP-профиля Vanessa. Это не обязательная часть обычного ручного первого запуска. Имя файла не является доказательством его внутреннего идентификатора или совместимости.

Для самого первого учебного результата достаточно: отдельного каталога исходников, одного простого тестового модуля и YAxUnit **или** одной безопасной feature и Vanessa Automation. Инструменты можно осваивать последовательно, а не одновременно.

## 3. До начала: что нужно получить у владельца базы

Перед изменением базы должны быть известны следующие сведения. Если ты уже дал их агенту и разрешил нужные действия, повторно подтверждать каждый пункт не нужно:

1. Подтверждение, что `C:\BASES\DEMO\bp1` — именно выделенная тестовая БП 3, а не рабочая копия.
2. Окно обслуживания: в этот момент в базе не должны выполняться важные работы другими пользователями.
3. Пользователь 1С и способ входа с правами, достаточными для просмотра состава расширений; отдельно — явное разрешение на изменение конфигурации, если компонента нет.
4. Где лежит резервная копия до изменения и как она будет проверена. Для файловой базы это должна быть успешная выгрузка базы средствами Конфигуратора либо другой согласованный восстановимый бэкап; одной копии открытого `1Cv8.1CD` недостаточно.
5. Подтверждение версии платформы 1С и релиза БП из окна «О программе»/Конфигуратора.
6. Согласование, какие инструменты разрешены в первом этапе: только YAxUnit; YAxUnit + Smoke; Vanessa EPF без расширений; либо отдельный MCP-профиль.

Пароли, строки подключения с паролями и файлы с секретами в эту инструкцию, репозиторий и отчёты не копируются.

## 4. Сначала инвентаризация базы — без изменений

### 4.1. Как открыть базу безопасно

1. Закрой свои сеансы `bp1`; если работают другие пользователи, согласуй окно обслуживания. Не завершай чужие сеансы принудительно.
2. Запусти **Конфигуратор** для уже зарегистрированной базы `bp1`. Не открывай и не копируй файл `1Cv8.1CD` напрямую в проводнике.
3. Введи согласованные учётные данные.
4. Ничего не загружай и не нажимай команды обновления/реструктуризации.

### 4.2. Что зафиксировать

В Конфигураторе открой раздел управления расширениями конфигурации (в разных версиях платформы название пункта может немного отличаться, обычно это **Конфигурация → Расширения конфигурации**). Сделай один скриншот списка и выпиши для каждого расширения:

- отображаемое имя и синоним;
- назначение, версию (если показывается), состояние/подключённость;
- безопасный режим и защиту от опасных действий — только как факт, без изменения;
- есть ли среди них YAxUnit, Smoke, VAExtension или расширение с неизвестным, но похожим назначением.

Отдельно зафиксируй версию платформы и конфигурации. Если список расширений в этом сеансе недоступен, попроси у администратора скриншот/экспорт именно этого списка. Не замещай инвентаризацию повторной загрузкой `.cfe`.

### 4.3. Решение после инвентаризации

| Наблюдение | Действие |
|---|---|
| Компонент отсутствует, есть бэкап и разрешение | можно готовить точечную установку только этого компонента |
| Компонент уже есть | ничего не переустанавливать; сначала сравнить имя, версию и назначение с нужным сценарием |
| Похожее, но неидентичное расширение | остановиться и уточнить у владельца/разработчика: это может быть другая ветка или локальная доработка |
| Нет прав, бэкапа или согласования | только подготовить исходники и тесты вне базы; установку отложить |
| Неясна совместимость с БП/платформой | провести отдельную проверку совместимости на согласованной копии, а не в `bp1` |

## 5. Где хранить исходники тестов

Создай **отдельный проект исходников вне каталога базы**. Пример будущего пути: `C:\1C-Projects\bp1-tests`.

Это только пример расположения, создавать каталог по этой инструкции сейчас не требуется. В таком проекте удобно держать:

```text
bp1-tests/
  README.md                 # цель тестов и как их запускать
  unit/                     # собственные модули YAxUnit
  features/                 # собственные сценарии Vanessa (*.feature)
  .bsl-flow/reports/          # локальные результаты, исключены из Git
  .bsl-flow/evidence/         # скриншоты/версии/журналы первого запуска без секретов
```

Тестовые модули должны быть отдельными от внутренностей YAxUnit: не изменяй модули движка, не размещай бизнес-тесты внутри его расширения. Свои тесты располагаются в собственной поставляемой доработке/расширении тестов по согласованной архитектуре; исходный BSL хранится в отдельном проекте. Так обновление YAxUnit не уничтожит тесты.

## 6. Установка YAxUnit, если он отсутствует

Этот раздел выполняется **только** если инвентаризация доказала отсутствие YAxUnit, имеется проверенный бэкап и владелец базы разрешил изменение. Официальная документация YAxUnit для установки в Конфигураторе предписывает загрузить `.cfe`, затем снять у расширения безопасный режим и защиту от опасных действий — это разрешённая, но изменяющая базу операция. [Официальная инструкция YAxUnit](https://bia-technologies.github.io/yaxunit/docs/getting-started/install/).

1. Сохрани результат бэкапа и скриншот списка расширений «до» в согласованном месте.
2. В Конфигураторе снова открой список расширений и выбери команду добавления/загрузки расширения из файла.
3. Выбери строго `C:\YAxUnit\YAxUnit-25.12.cfe`.
4. До подтверждения прочитай предупреждения платформы. Если появилось неожиданное изменение базовой конфигурации, реструктуризация, конфликт расширений или иное расширение, отменяй операцию и фиксируй текст предупреждения.
5. Для добавленного расширения установи только два требуемых доверительных параметра: отключи безопасный режим и защиту от опасных действий. Это делается **только для YAxUnit**, а не глобально для всей базы и не для всех расширений.
6. Сохрани изменение конфигурации базы данных обычным штатным способом Конфигуратора. Не меняй прочие свойства расширений и не выполняй обновление ранее существующих компонентов.
7. После завершения вернись к списку расширений, сделай скриншот «после» и проверь, что появился ровно один ожидаемый компонент.
8. Запусти сеанс «1С:Предприятие» под согласованным пользователем и найди форму/команду YAxUnit по официальному руководству или в назначенной подсистеме. Если команда не доступна, не меняй роли наугад: зафиксируй пользователя, роли и сообщение/скриншот, затем согласуй права.

`Smoke-25.12.cfe` на этом шаге не загружается. Официальная документация рассматривает Smoke как отдельное расширение для запуска дымовых тестов; оно ставится только при принятом решении о таком прогоне. [Документация Smoke](https://bia-technologies.github.io/yaxunit/docs/features/smoke/).

## 7. Первый осмысленный тест YAxUnit

Цель первого теста — доказать весь путь «свой тест обнаружен → выполнен → получен результат», а не получить зелёный статус при нуле тестов.

1. Выбери простую детерминированную функцию собственной доработки или изолированной учебной обработки. Она не должна проводить документы, удалять данные, вызывать обмены, HTTP-сервисы или менять настройки БП.
2. Создай отдельный тестовый модуль в собственной тестовой доработке. В нём должна быть экспортная процедура `ИсполняемыеСценарии`: YAxUnit использует её для регистрации тестов. Инициализацию и создание данных в ней не выполняют, поскольку она вызывается до исполнения тестов. [Регистрация тестов YAxUnit](https://bia-technologies.github.io/yaxunit/docs/getting-started/first-test/).
3. Зарегистрируй **один** тест и проверь известный результат функции, например расчёт/нормализацию без обращения к данным базы. Само тестовое имя должно описывать ожидаемое поведение.
4. В форме YAxUnit отфильтруй запуск так, чтобы был виден именно этот один тест. До запуска убедись, что счётчик найденных тестов равен `1`, а не `0`.
5. Запусти тест. Хороший результат первого запуска: один найденный, один выполненный, один успешный тест; в отчёте есть имя теста и время запуска.
6. Сохрани отчёт (например, JUnit/XML или JSON — формат выбирается в настройках запуска YAxUnit) и скриншот итоговой формы. Не включай в отчёт пароли или персональные данные.

Если найдено `0` тестов, это не PASS: проверь размещение модуля, экспортность и регистрацию в `ИсполняемыеСценарии`, а также фильтры. Если тест упал, фиксируй текст ошибки и не «исправляй» результат выключением проверки.

### Небольшой пример для первого знакомства

Для проверки самого движка можно начать с редактора тестов YAxUnit в режиме «Предприятие», если он доступен в установленной версии, не создавая ради знакомства дополнительное расширение. Открой команду «Запуск тестирования» и редактор тестов; способы запуска описаны в [официальном руководстве](https://bia-technologies.github.io/yaxunit/docs/getting-started/run/). Пример кода:

```bsl
Процедура ИсполняемыеСценарии() Экспорт
    ЮТТесты.ДобавитьТест("ПроверкаПервогоЗапуска");
КонецПроцедуры

Процедура ПроверкаПервогоЗапуска() Экспорт
    Получено = 7 + 5;
    ЮТест.ОжидаетЧто(Получено).Равно(12);
КонецПроцедуры
```

Ожидается один успешный тест. Для проверки, что assertion действительно работает, временно замени ожидаемое `12` на `13`: должен получиться один упавший тест. Верни `12` и повтори. Это проверяет подключение движка и механизм assertions, **не бизнес-логику БП**. Постоянные тесты доработок затем сохрани с исходниками проекта; редактор не заменяет регрессионную поставку. Код использует документированные API, но именно в твоей базе пока не запускался.

## 8. Первый запуск Vanessa Automation без установки расширений

Для первого знакомства Vanessa достаточно открыть внешнюю обработку с диска: `C:\vanessa-automation\vanessa-automation.epf`. EPF оставляй на диске; его открытие не означает, что VAExtension или `client_mcp` уже нужны.

1. С согласованным пользователем открой `bp1` в режиме «1С:Предприятие».
2. Открой внешнюю обработку штатной командой платформы («Файл → Открыть» либо разрешённый в вашей БП путь к внешним обработкам). Выбери `C:\vanessa-automation\vanessa-automation.epf`.
3. Если платформа спросит о доверии к внешней обработке, не добавляй доверие глобально. Зафиксируй текст предупреждения и согласуй с администратором точечный безопасный способ открытия для этого файла.
4. На основной форме Vanessa работай с вкладкой запуска сценариев: именно там сценарии загружаются и выполняются. [Краткое описание формы VA](https://pr-mex.github.io/vanessa-automation/dev/MainHelp/1.2.043.1/%D0%93%D0%BB%D0%B0%D0%B2%D0%B001/%D0%97%D0%BD%D0%B0%D0%BA%D0%BE%D0%BC%D1%81%D1%82%D0%B2%D0%BE%D0%A1VanessaAutomation%D0%9E%D1%81%D0%BD%D0%BE%D0%B2%D0%BD%D1%8B%D0%B5%D0%AD%D0%BB%D0%B5%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%D0%A4%D0%BE%D1%80%D0%BC%D1%8B.MD).
5. Для обучения возьми новую собственную feature в проекте исходников, а не feature из каталога `C:\vanessa-automation\features`: этот каталог является библиотекой/набором самопроверок VA и не является безопасным набором сценариев для БП.
6. Первый сценарий должен быть наблюдательным: открыть начальную форму, убедиться в видимом заголовке/элементе и закрыть форму без записи. Перед запуском прочитай каждый шаг: слова «создать», «записать», «провести», «удалить», «выполнить обмен» означают, что сценарий не годится для первого безопасного прогона.

Перед подключением тест-клиента проверь сам механизм сценариев. Создай в проекте файл `features/engine-check.feature` в UTF-8 с таким содержимым; оба шага найдены в скачанной библиотеке VA:

```gherkin
# language: ru
Функционал: Проверка подключения движка Vanessa

Сценарий: Сохранение и проверка учебной строки
    Дано я запоминаю строку "bp1-ready" в переменную "ПроверкаОкружения"
    Тогда переменная "ПроверкаОкружения" имеет значение "bp1-ready"
```

Загрузи этот файл в Vanessa и выполни: ожидается один успешный сценарий с двумя шагами. Для отрицательной проверки временно замени только ожидаемую строку второго шага на `другое`: сценарий должен упасть. Верни `bp1-ready`. Проверка работает с переменной сценария и не создаёт документы БП; она **не доказывает подключение тест-клиента или работу форм**. После неё выполни отдельную проверку клиента из следующего раздела. Сценарий здесь подготовлен, но в `bp1` не запускался.

Имена шагов подтверждены локальными примерами `features/Libraries/ОбъектыКонфигурации/ТестСозданияОбъектов.feature` и `features/Libraries/ИнициаторДанных/БиблиотекаШаговИнициаторДанных.feature`; эти чужие наборы целиком запускать не нужно. Общая документация — в [руководстве Vanessa Automation](https://pr-mex.github.io/vanessa-automation/dev/).

## 9. Менеджер и клиент тестирования

Vanessa работает как минимум с двумя независимыми сеансами 1С:

- **Тест-менеджер** — сеанс, в котором открыта Vanessa Automation и который координирует сценарий.
- **Тест-клиент** — отдельный сеанс, в котором выполняются действия пользователя и наблюдается интерфейс.

Для первого простого последовательного учебного случая оба сеанса могут подключаться к одному `bp1`, но это не делает их одним сеансом. Нужны отдельные профили/запуски и права, достаточные для входа выбранного пользователя. Не выдумывай названия пунктов меню или параметры запуска: они зависят от версии VA и платформы. Используй экран настройки тест-клиента и официальную главу о запуске клиента; в ней описаны, в частности, таймаут запуска и диапазон портов. [Настройки тест-клиента VA](https://github.com/Pr-Mex/vanessa-automation/blob/develop/docs/JsonParams/JsonParamsRU.md).

Порядок безопасной настройки:

Для управления клиентом сеанс менеджера должен быть запущен в режиме `/TESTMANAGER`; простое открытие EPF в обычном сеансе этого не гарантирует. Укажи этот параметр при ручной настройке запуска менеджера. Режим клиента тестирования — `/TESTCLIENT`; штатная настройка клиента в Vanessa должна формировать соответствующий запуск. Это параметры режимов платформы, а не аргументы публичного Unica. Пример менеджера опубликован в [официальной документации VA](https://pr-mex.github.io/vanessa-automation/dev/AI/).

1. В менеджере создай один профиль с понятным названием, например «bp1-тонкий-клиент-учебный».
2. Укажи только согласованный путь/строку подключения к `bp1`, тип клиента и пользователя без публикации пароля в feature или отчёте.
3. Выбери запуск одного тест-клиента; не включай параллельность.
4. Подключи клиента и визуально убедись, что открылся отдельный сеанс именно нужной базы и под ожидаемым пользователем.
5. Только после этого запиши в Vanessa свой сценарий открытия конкретной безопасной формы. Используй фактически наблюдаемый заголовок и штатный шаг `Тогда открылось окно "точный заголовок формы"`; текст внутри кавычек замени реальным ожидаемым заголовком. Проверь его библиотеку/контекст, сохрани `.feature`, закрой и повторно открой форму через этот сценарий. Не выдавай проверку переменной из раздела 8 за эту проверку UI.
6. После прогона штатно отключи тест-клиент и закрой сеансы.

Если клиент не подключается, сохраняй лог/текст ошибки и настройки без секретов. Не «лечи» проблему добавлением расширений, отключением безопасности глобально или повторными параллельными запусками. В VA статус «не найдено ни одного сценария» — отдельный неуспешный для проверки результат (статус 3), а не удачный прогон. [Статусы выполнения VA](https://github.com/Pr-Mex/vanessa-automation/blob/develop/docs/ReturnStatus/ReturnStatus.md).

## 10. Когда потребуются VAExtension и client_mcp

### VAExtension

Устанавливается только если выбранный сценарий/профиль текущей версии VA явно требует возможности расширения, и это подтверждено документацией или наблюдаемым сообщением VA. Тогда повтори процедуру из раздела 6, но для одного `C:\vanessa-automation\VAExtension.1.29.cfe`: новая инвентаризация, бэкап, явное разрешение, точечная установка, проверка списка «после». Не переносите настройки доверия YAxUnit на VAExtension автоматически.

### client_mcp

`C:\vanessa-automation\client_mcp.cfe` относится только к отдельно согласованному MCP-профилю. Его не ставят для обычных ручных VA-сценариев. До установки нужно подтвердить:

1. какая версия Vanessa и платформы используется;
2. какой именно профиль MCP должен работать и что он делает;
3. внутреннее имя расширения по факту загрузки/документации, а не по имени файла;
4. требуемые права, порт/сетевая политика и допустимые действия;
5. совместимость в выделенной копии базы.

Публичный runtime-инструмент Unica позволяет загружать CFE, но проверенная возможность «получить список установленных расширений» для него отсутствует. Его операция над расширениями меняет свойства синхронизации и потому является изменяющей, а не способом чтения. Значит, не применяй его для инвентаризации и не используй как замену Конфигуратору/скриншоту администратора.

## 11. Доказательства успешного первого этапа

Собери в `.bsl-flow/evidence/` отдельного проекта (либо в согласованной папке) следующие материалы без секретов:

1. дата, версия платформы, версия БП и учётная запись/роль в обезличенном виде;
2. скриншот списка расширений до и после каждого реально выполненного изменения;
3. идентификатор и результат проверенного бэкапа;
4. для YAxUnit: отчёт, где видно `найдено = 1`, `выполнено = 1`, `ошибок = 0`, и имя собственного теста;
5. для VA: путь к собственной feature, количество сценариев больше нуля, имя сценария, результат и лог; отдельно скриншот подключения тест-клиента;
6. список того, что сознательно **не** устанавливалось: например Smoke, VAExtension, client_mcp.

«PASS» допустим только при ненулевом числе реально выполненных собственных тестов/сценариев и сохранённом результате. Для согласованного интерактивного пилота сохрани observation через `Save-1CInteractiveTestPilot.ps1`: helper добавит immutable history и обновит `test-setup/current.json`, но оставит unattended readiness заблокированной без свежего JUnit/receipt. Открытая обработка, зелёная форма без запуска, `0` сценариев или отсутствие исключения сами по себе не подтверждают готовность окружения.

## 12. Краткий маршрут новичка

1. Получить разрешение, бэкап и данные о версии базы.
2. Снять инвентаризацию расширений в Конфигураторе без изменений.
3. Если YAxUnit отсутствует — согласованно и точечно установить только YAxUnit; если есть — не переустанавливать.
4. Создать/согласовать внешний проект исходников для собственных тестов; не работать в `bp1` и не использовать `_cfe_src`.
5. Написать и выполнить один безопасный, найденный YAxUnit-тест; сохранить отчёт.
6. Отдельно открыть VA EPF, настроить один тест-клиент и выполнить одну наблюдательную feature без изменений данных.
7. Только после успешных двух доказательств обсуждать Smoke, VAExtension или MCP.

## 13. Как поручить настройку агенту

После установки BSL Flow v0.6.1 открой в Codex отдельный каталог своего проекта и напиши, например:

> Подготовь тестовое окружение этого проекта для файловой базы C:\BASES\DEMO\bp1. YAxUnit лежит в C:\YAxUnit, Vanessa — в C:\vanessa-automation. Сначала проверь установленный состав и совместимость. Переиспользуй подходящие компоненты, предложи установку только недостающих. Покажи, какие права и изменения защиты нужны, и выполни по одному безопасному учебному тесту. Не используй каталог базы как проект и не запускай полный Smoke.

Это запрос на подготовку, не команда немедленно загружать все расширения. Дальше агент сам проверяет каталоги, использует имеющуюся информацию о базе и называет только недостающие сведения. Если установка и конкретные параметры доверия ещё не разрешены, достаточно одного согласования их точного объёма.

В проверенном текущем Unica нет подтверждённого read-only API списка расширений. Поэтому для первого запуска может потребоваться список/свойства из Конфигуратора либо отдельно согласованный короткий осмотр интерфейса агентом. Это конкретное ограничение автоматизации, а не обязательный ручной шаг для каждого будущего проекта. При появлении поддерживаемого API агент использует его; при неизвестном состоянии никогда не загружает CFE вслепую.

Установленные в общей базе движки служат нескольким проектам. Новый проект добавляет свои исходники, тесты и параметры запуска, а не ещё одну копию YAxUnit. При изменении платформы, версии движка или состава расширений нужна повторная проверка совместимости. Дальнейшие проверки логики идут через YAxUnit, сценарии интерфейса — через сохранённые Vanessa feature; первичная настройка не делает computer-use основным способом тестирования.
