# План развития BSL Flow до управляемого Agentic SDLC

Дата: 2026-09-09. Исходная версия: `0.6.1`, commit `198da1c`.
Статус исходного документа: план, согласованный перед реализацией. По последующему поручению реализована development-версия `0.7.0-dev.1`; текущее выполнение milestones и ограничения отражены в [VERIFICATION.md](VERIFICATION.md). Текст плана ниже сохранён как исходное основание работ.

## 1. Цель и критерий готовности

Пользователь ставит задачу один раз. В управляемом режиме BSL Flow определяет необходимый маршрут, запускает этапы, проверяет их результаты и продолжает до принятого результата либо конкретной остановки. Пользователь не напоминает о спецификации, review или тестах. После прерывания продолжение опирается на сохранённое состояние и фактический результат предыдущего действия.

Первая целевая поставка считается готовой только после M0–M8 ниже, включая реальный сквозной пилот. Наличие нового CLI, зелёные unit-тесты контроллера и успешно выполненный engine smoke сами по себе не означают достижения этой цели.

Обязательное наблюдаемое поведение:

1. S/low проходит короткий маршрут без обязательной спецификации и внешнего review.
2. M/L/high-risk не допускаются к реализации без актуальной необходимой спецификации и разрешённого review.
3. Нельзя принять изменение по тестам от другой редакции кода или неполному набору обязательных критериев.
4. Изменённые требования и входы автоматически делают зависимые результаты устаревшими.
5. Остановка provider, отсутствие тестового инструмента, вопрос к пользователю и сбой бизнес-проверки имеют разные причины и следующие действия.
6. После неизвестного результата записи выполняется проверка состояния; запись не повторяется автоматически.
7. Повторное чтение состояния и повторная доставка одного результата не дублируют побочные эффекты.
8. Новая сессия может продолжить задачу без восстановления важных решений из переписки.
9. Приёмка проверяет текущую версию результата; финальное сообщение модели не является свидетельством успешной приёмки.

В первую поставку не входят распределённая очередь, веб-панель, несколько одновременно изменяющих одну базу задач, автоматические production-действия, смена основного языка проекта и собственный универсальный agent framework. Непрерывная работа после закрытия запускающего процесса — отдельное последующее расширение; `resume` в первой поставке обязателен.

## 2. Решение по архитектуре

Сохранить существующие шесть skills, шаблоны OpenSpec, независимую критику, reconciliation, тестовые helpers, настройки окружения и журнал субагентов. Добавить небольшое общее ядро управления задачей и один подтверждённый адаптер исполнения этапов.

Выбранное направление: **детерминированный контроллер с последовательным циклом исполнения; LLM выполняет содержательную работу внутри разрешённого этапа**. Следующий этап, обязательность проверок и итоговый допуск вычисляются кодом.

| Вариант | Решение и причина |
| --- | --- |
| Дописать инструкции и добавить добровольный вызов `next` | Недостаточно: агент всё ещё может забыть вызвать проверку или остановиться раньше времени. |
| Контроллер + ограниченный host adapter | Основной путь: небольшой контролируемый цикл; можно переиспользовать существующие helpers. |
| Сразу новый распределённый оркестратор | Отложить: пока нет доказанной необходимости в очереди, сервисах и нескольких исполнителях. |

Два явно различаемых режима:

- `assisted`: существующие skills помогают агенту; документация не обещает принудительное соблюдение всех этапов.
- `managed`: задачу ведёт контроллер, который сам вызывает поддержанный adapter, принимает наблюдаемые результаты и применяет gates. Неподтверждённый adapter не может называться managed.

Первым реализовать Codex CLI adapter на базе `codex exec`; возможность запуска подтверждена локальной справкой, фактическая изоляция и жизненный цикл проверяются в M0. Существующий OpenCode adapter и специальный OpenCode reviewer сохранить. Полноценный managed OpenCode dispatcher добавлять только после первого сквозного результата, по тому же контракту; существующий assisted OpenCode не должен сломаться.

Встраивание в обычную desktop-сессию начинается с `1c-task`: один вызов managed запуска и показ состояния. Программный цикл, а не родительская беседа, отвечает за продолжение этапов. Hooks могут улучшать UX и допуск операций, но не являются единственным основанием корректности.

## 3. Граница гарантий

Контроллер гарантирует соблюдение переходов и приёмку результата только для зарегистрированной managed-задачи и операций через подтверждённые адаптеры. Он не утверждает, что блокирует действия человека, произвольного внешнего терминала или другого процесса за пределами этого контура.

Для managed требуется разделить область исходников, доступную worker на запись, и авторитетное состояние контроллера. Предпочтительно: worker работает в выделенной Git worktree, а состояние хранится в основном project root, вне writable roots worker. Код контроллера и зафиксированная политика берутся из установленного пакета, а не из изменяемой worker копии. Рабочая копия не получает разрешение изменять policy, входные требования, журнал, чужие worktrees или основную базу.

Это требование к проверяемым permissions, а не к формулировке prompt. Если M0 не докажет необходимые ограничения на выбранном хосте, managed adapter остаётся BLOCKED. Усиление изоляции выбирается по результатам M0; нельзя незаметно заменить её обещанием агента.

Изоляция охватывает всю цепочку исполнения: изменяемые worker тесты, Git hooks, build scripts и их дочерние процессы не запускаются с доступом controller к authoritative state. Controller вызывает установленный доверенный adapter, а тот исполняет source/test code в подтверждённом ограниченном контуре. Конкретный OS/sandbox механизм выбирается в M0; capability runtime adapter отдельно проверяется в M5. Для FILE runtime допустим доступ к разрешённой тестовой базе, но не к state/policy controller. Нельзя исполнить изменяемый `.ps1` прямо в процессе controller или считать лишение LLM инструмента `edit` достаточным ограничением тестового runner.

Подписывание JSON локальным секретом, доступным тому же worker, не считается защитой. Произвольный `PASS` от модели не импортируется как authoritative gate.

Разрешение на реализацию framework не разрешает установку в глобальные каталоги, публикацию, изменение базы или снятие действующего временного ограничения Unica. Все необходимые разрешения для пилота привязываются к точному маршруту и цели. При отсутствии разрешения можно готовить код/фикстуры, но соответствующий runtime gate остаётся BLOCKED.

## 4. Минимальные контракты ядра

Это проектируемые имена и форматы, а не уже существующий API. Исполнитель сначала фиксирует schemas и тестовые fixtures, затем пишет поведение. Имена можно согласованно уточнить до M2, но не менять независимо в разных частях реализации.

### 4.1. Размещение и совместимость

Предпочтительное размещение: новая устанавливаемая skill `global/skills/1c-task/`, содержащая entrypoint, общее ядро, JSON schemas, host adapters и короткие references. Язык ядра — PowerShell, совместимый с 5.1 и 7; не вводить новый runtime без подтверждённого препятствия.

Существующие helpers остаются вызываемыми отдельно. Контроллер оборачивает их и добавляет task/attempt identity, обязательность evidence и свежесть входов. Не копировать Review.Common или TestEvidence.Common целиком в новое ядро. Общие функции извлекать только при реальном использовании несколькими модулями.

Рабочие данные задачи:

```text
<project>/.bsl-flow/tasks/<task-id>/
  revisions/000001.json       # неизменяемый полный снимок принятого состояния
  revisions/000002.json
  current.json                # производная, восстанавливаемая ссылка/сводка
  inputs/                    # сохранённые редакции исходного запроса/уточнений
  attempts/<attempt-id>/
    start.json               # записывается до запуска действия
    result.json              # единственный terminal result попытки
    raw/                     # исходные ответы инструментов и отчёты
  acceptance/                # receipt приёмки конкретной версии результата
```

Источником истины являются последовательные immutable revisions и зарегистрированные attempts; `current.json` не является отдельным источником истины. Каждая revision фиксирует ссылку/хеш предыдущей. Выбирается последняя целая непрерывная цепочка, а не файл с максимальным timestamp. Неясная/повреждённая история даёт BLOCKED и сохраняется для диагностики.

Хранение — локальный filesystem, один writer под эксклюзивной блокировкой. Без SQLite, event bus и отдельного event-sourcing framework. Публикация revision: временный файл → атомарное создание без перезаписи под lock; после этого обновление производной current. Прерывание на каждом шаге проверяется тестом. Наличие старого lock-файла не доказывает работающий процесс; занятый OS lock не обходится.

OpenSpec продолжает хранить только spec и optional design. Sidecars review сохраняются в change. `tasks.md` не добавляется. Для S/low достаточно сохранённого запроса и компактного brief в task record.

### 4.2. Состояние задачи

Минимальные группы полей:

| Группа | Содержание |
| --- | --- |
| Identity | `schema_version`, `task_id`, `revision`, project/worktree identity, baseline commit, revision chain. |
| Intent | Ссылка и хеш запроса/уточнений, `intent_revision`, режим `analysis_only` или `implement`, provenance разрешения. |
| Route | Complexity, risk, impact flags, обоснование со ссылками на исследование, вычисленные обязательные этапы. |
| Policy | Версия framework и снимок эффективной policy, ссылки на применимые правила проекта. |
| Progress | `stage`, `status`, активная попытка, использованные лимиты, blocker/question. |
| Inputs | Хеши spec/design, состава исходников, проверяемого diff и применимых конфигураций. |
| Verification | Список обязательных критериев и выбранных проверок, связь с intent revision. |
| Evidence | Ссылки на попытки и проверенные receipts; наблюдаемый scope и dependency hashes каждого результата. |
| Outcome | Acceptance receipt либо точная причина остановки и разрешённое следующее действие. |

Stages: `inspect`, `spec`, `spec_review`, `implement`, `code_review`, `verify`, `acceptance`. Ненужные этапы исключаются policy, а не помечаются фиктивным PASS.

Statuses: `ready`, `running`, `needs_input`, `blocked`, `failed`, `completed`, `cancelled`. Устаревание — свойство evidence, из которого вычисляется первый необходимый повторный этап. Не создавать отдельное состояние для каждой комбинации ошибки, этапа и инструмента.

`analysis_only` заканчивается принятым анализом/планом и не получает implementation capability. Продолжение с реализацией требует сохранённого явного разрешения; уже действующее разрешение повторно не спрашивается.

`revision` — номер сохранения state для конкурентного доступа, а не автоматический повод инвалидировать все gates. Свежесть определяется dependency hashes. Отдельная `authorization_revision` меняется при уточнении разрешений; `intent_revision` — при изменении требуемого поведения/scope. Разрешение реализовать уже подготовленную неизменённую спецификацию не должно само по себе требовать нового оплачиваемого spec-review.

Для `analysis_only` путь заканчивается после заказанного результата: `inspect → acceptance` для анализа, либо `inspect → spec → required spec_review → acceptance` для спецификации. Implementation/code/runtime gates в analysis acceptance не требуются. Историческая приёмка анализа сохраняется отдельно от будущей приёмки реализации. Из `completed` разрешён `Update` с подтверждённым продолжением этой задачи; затем `Next` выбирает первый недостающий этап. Completed implementation не открывается молча: новая работа требует нового request ID либо явного Update с новой intent revision.

### 4.3. Маршрутизация

| Класс/риск | Артефакт | Spec review | Code review |
| --- | --- | --- | --- |
| S/low | brief | Optional, если не усилено пользователем/проектом | По конкретному риску |
| S/medium | spec | Optional по существующей политике S | По конкретному риску |
| M/low или medium | spec | Required | По policy проекта и риску |
| L при любом риске; любой класс/high | spec + design | Required | Required |

Это устраняет неоднозначность S/medium, сохраняя действующее правило: medium требует spec, но само по себе не делает review всех S обязательным. Высокий риск всегда сильнее размера задачи.

LLM предлагает классификацию с evidence; контроллер проверяет минимальные ограничения: изменение прав, миграция/удаление данных и другие явно критические последствия не могут пройти S/low; posting и data exchange требуют интеграционной проверки; изменение form flow требует UI evidence. Карта flags должна быть короткой и покрыта примерами, а не эвристикой по числу строк. Непонятные правила идентичности, группировки, замещения или частичного успеха → `needs_input`, без догадки.

При обнаружении большего scope риск и обязательные проверки повышаются автоматически. Автоматическое понижение для обхода blocker запрещено. Обоснованное изменение scope/обязательных критериев создаёт новую intent/policy revision и инвалидирует зависимые результаты.

### 4.4. Команды и переходы

Один entrypoint `Invoke-BSLFlowTask.ps1`, аргументы передаются структурированно/файлами, без генерации shell-строк из model output.

| Action | Контракт |
| --- | --- |
| `Start` | Проверить project root/режим, зарегистрировать запрос и identity по обязательному caller `request_id`; не считать наличие spec готовностью. Возвращать стабильный task ID. |
| `Status` | Прочитать/проверить сохранённое состояние, показать актуальность результатов и blockers; не запускать LLM/1С. |
| `Next` | Детерминированно вычислить следующий разрешённый этап и недостающие условия; не выполнять его. |
| `Run` | Последовательно исполнять `Next` через adapter, сохранять attempts и принимать результаты до terminal/pause/limit. Пользователь не запускает каждый этап отдельно. |
| `Record` | Импортировать только результат зарегистрированной попытки по контракту adapter; произвольный `passed=true` не принимается. |
| `Update` | Принять уточнение/ответ/разрешение через доверенный host input; проверить task ID, ожидаемую revision и question ID, если ответ связан с вопросом. Создать новую revision и пересчитать dependencies; не исполнять следующий этап автоматически внутри Update. |
| `Accept` | Заново проверить все обязательные условия, входы и точный результат; сформировать receipt приёмки. Не merge/push/deploy. |
| `Resume` | Сверить текущие входы, незавершённые попытки и побочные эффекты; продолжать только когда известен допустимый следующий шаг. |
| `Cancel` | Зафиксировать отмену, запретить новые dispatch, остановить только принадлежащий задаче локальный процесс и сохранить evidence. Уже отправленная операция могла примениться; cancellation не доказывает rollback или отсутствие записи. |

У `Run` должны быть конечные лимиты попыток/времени. По умолчанию не более одного исправления после содержательной неудачи, как в текущей policy. Лимит не превращает незавершённую задачу в completed. Нет `ForcePass`, прямого `SetStage` или автоматической замены unavailable reviewer.

Новый versioned CLI envelope содержит `schema_version`, `task_id`, `revision`, `status`, `stage`, `next_action`, `blockers`, `evidence_refs`. Вердикт приёмки (`PASS`, `PASS_WITH_LIMITATIONS`, `FAIL`, `BLOCKED`) отделён от task status. `completed` допускается только при принятом запрошенном результате; `PASS_WITH_LIMITATIONS` не закрывает обязательный отсутствующий критерий.

Коды нового entrypoint: `0` — успешная команда чтения/регистрации/обновления либо принятый результат Run/Resume/Accept; `10` — Run/Resume/Accept остановлен в needs_input; `11` — BLOCKED; `12` — доказанный FAIL; `13` — исполнение отменено; `2` — невалидный input/schema; `3` — конфликт identity/revision или занятый writer; `4` — внутренняя ошибка controller. Status/Next могут штатно вернуть `0` и envelope текущего blocked state: adapter всегда разбирает envelope. Сам Cancel при успешной регистрации отмены возвращает `0`; последующий Run этой задачи — `13`. Старые helpers сохраняют свои CLI contracts; преобразование кодов выполняется в adapter, не эвристикой «ненулевой exit означает provider crash».

Правила повторов фиксированы:

- `request_id` — обязательный UUID, сформированный host до первого Start; `task_id` равен ему внутри канонического project root. Повтор Start с тем же ID и теми же исходными input hashes возвращает уже созданную задачу без второго запуска. Тот же ID с другим запросом — конфликт; новый UUID означает намеренно новую задачу, даже если текст совпадает.
- Record идентифицируется парой task/attempt. Повтор того же нормализованного result и набора raw hashes — no-op с прежним receipt. Конфликтующий terminal result той же attempt отклоняется с сохранением диагностики; для повторного исполнения требуется новая attempt.
- Update имеет `input_event_id`, ожидаемую task revision, kind (`clarification`, `authorization`, `scope_change`) и provenance исходного user event. Повтор принятого event ID с тем же payload возвращает прежний outcome даже после продвижения revision; конфликтующий payload отклоняется. Новый event со старой revision не применяется молча.
- Host adapter отличает user input от worker output. Worker не может выдавать свой текст за authorization или ответ пользователя. CLI принимает explicit input file от доверенного оператора; отсутствие доказуемого происхождения host event даёт needs_input. В generated worker profile Update/authoritative state недоступны.
- При вопросе сохраняются `question_id`, текст, конкретный недостающий факт и input revision. Ответ на закрытый или устаревший вопрос не применяется автоматически к новой ситуации.

### 4.5. Попытка и adapter

Перед каждым запуском контроллер сохраняет `attempt_id`, stage, входные хеши, executable/version, requested model/effort, permissions profile, рабочую директорию, выбранные проверки/target, start time и operation identity. Только после сохранения start разрешается действие.

Adapter возвращает terminal status, реально наблюдавшиеся входы/выходы, пути к raw evidence, process/session identity, exit status, обнаруженные побочные эффекты и usage с provenance. Структурный JSON модели — лишь предложение результата; controller сам проверяет gate. Unknown usage не равен нулю.

Codex worker получает только контекст этапа и нужный skill. Review выполняется отдельным контекстом; для spec-review остаётся существующий OpenCode wrapper с текущей project configuration. Не менять default reviewer на Sol из-за выбора модели-исполнителя этого плана.

Этапы исследования/review запускаются read-only; необходимые Markdown/JSON артефакты из проверенного structured output пишет controller. Implementation worker пишет только в свою source worktree. Процессы не получают произвольный runtime-маршрут или расширение разрешений из response модели. Профили запуска локальны для run, глобальные настройки пользователя не переписываются.

Путь к CLI, особенности launcher `.ps1/.cmd/.exe`, stdin, encoding, timeout, cancellation и JSON events должны быть проверены на Windows. `--last` и поиск «последней похожей сессии» запрещены для восстановления: только сохранённая точная identity.

Внутри `spec_review` исполняется явный подмаршрут без новых OpenSpec stages: сохранить reviewed draft → вызвать существующий reviewer wrapper один раз → отдельный author/reconciler context проверяет каждое замечание по original task и source evidence → controller применяет только обоснованные изменения spec/design и сохраняет reconciliation → исправленный Test-1CSpecFinal проверяет draft-to-final binding. Critic read-only и не выполняет исправления. Draft hashes остаются неизменными; утверждённая reconciliation связывает их с final hashes. Такой переход не запускает новый полный review автоматически. Внешнее изменение входов вне зарегистрированной reconciliation делает результат stale; фундаментальное изменение требований требует новой intent revision и отдельного решения о новом review.

Контракт code review узкий: task/attempt identity, original/spec hashes, точный diff/source manifest, `PASS|REVISE|BLOCK`, findings с ID/severity/file/line/описанием сценария/evidence; без повторения score/overengineering framework. Непроходной verdict без адресуемых findings не является usable review. Основной инженер через отдельный reconciler принимает или отклоняет каждый finding с evidence. При неизменённом diff обоснованное отклонение всех findings допускается с отдельным final reconciliation receipt. Если код исправлен, нужен новый независимый review актуального полного diff с фокусом на исправления и новые риски; это максимум один correction/recheck round. Spec-review при этом не повторяется, если его зависимости не изменились. Незакрытые замечания или исчерпанный лимит останавливают работу; запись автора `addressed` без свежего review изменённого diff не разрешает acceptance. Этот контракт в M3 фиксируется schema и negative fixtures, а не вторым универсальным review engine.

### 4.6. Актуальность evidence и приёмка

Обязательность evidence определяется intent + route + заранее выбранным verification profile, не наличием параметра при сохранении результата. Минимальный профиль содержит criterion ID, требуемое наблюдение, вид проверки, exact selection, обязательные raw reports, source/target scope и причину выбранного уровня.

Каждый gate связывается с конкретным набором зависимостей. Spec-review — с отправленными байтами запроса/spec/design и зафиксированной policy. Code review — с final spec и точным diff. Тесты — с критериями, test selection, исходниками/артефактом, конфигурацией runner и наблюдаемой целью. Acceptance — со всей необходимой цепочкой.

Source manifest включает релевантные tracked и untracked файлы в объявленном source-set, удаления, пути и SHA-256; учитываются BSL, metadata, тесты и конфигурация, влияющая на результат. Generated output исключается явным правилом. Общего HEAD недостаточно для dirty worktree; строки версии расширения недостаточно для байтовой идентичности. Пустой, неполный или недоступный required source-set блокирует приёмку.

На старте первой managed-задачи разрешён либо чистый baseline, либо отдельно подтверждённый снимок dirty state. Автоматический stash, удаление и перенос пользовательских изменений запрещены. Повышать параллелизм нескольких задач до доказанной изоляции не нужно.

История старого PASS сохраняется, но он не действует на новые входы. Новый completion выполняет текущую проверку hashes и evidence requirements; `current.json` тестов проекта не является доказательством всех требований текущей задачи.

Для EPF/ERF сохранить static/native_build/roundtrip/native_load/behavior как разные gates. `behavior.required` приходит из task profile. Adapter разбирает raw results поддержанного инструмента; наличие пустого файла `{}` не доказывает runtime. Manual evidence явно помечается и допускается только для заранее обоснованного наблюдения; оно не повышает unattended readiness.

Acceptance receipt содержит task/intent revision, baseline, финальный source/diff/artifact manifest, policy version, выбранные gates и hashes raw evidence. Повторный `Accept` для того же результата идемпотентен. При новых входах старый receipt не применяется. Готовый receipt разрешает handoff результата; отдельно не разрешает публикацию или загрузку в клиентскую базу.

### 4.7. Восстановление

| Наблюдаемое состояние | Разрешённое продолжение |
| --- | --- |
| Действие точно не запускалось | Новый attempt после проверки прежних разрешений и актуальных входов. |
| Процесс ещё работает и identity подтверждена | Подключение к его результату; не запуск второго экземпляра. |
| Процесс завершён, raw result сохранён, Record не выполнен | Импорт сохранённого результата без повторения действия. |
| Код изменён, ответ worker потерян | Проверка diff/входов и gate реализации; не удалять результат и не считать его принятым. |
| Runtime мог применить изменения, receipt отсутствует | `blocked`, read-only проверка фактического состояния через поддержанный маршрут. |
| Запись подтверждена, post-check не выполнен | Выполнить только недостающую проверку, сохранив identity уже выполненной записи. |
| Бизнес-результат неверен | `failed`; ограниченное исправление в разрешённом scope, затем только инвалидированные проверки. |
| Неизвестно, произошёл ли побочный эффект | Никакого automatic retry; сохранить unknown и конкретный способ уточнения. |

Lease/PID не доказывает состояние базы. После Cancel новые действия запрещены, но уже начатая внешняя операция может закончиться; task сохраняет `cancelled` и unresolved effect state до read-only уточнения. Возобновление после отмены возможно только по явному Update от пользователя, не по автоматическому retry. Временное ограничение Unica сохраняется; cancellation controller не вызывает запрещённый `unica.runtime.job.cancel`.

## 5. Этапы реализации

Каждый этап — отдельная проверяемая поставка. Не переходить к зависимому этапу, пока его контрактный gate не выполнен. M1 можно делать параллельно с M0; shared files имеют одного writer.

### M0. Проверить фактический путь исполнения на хосте

Вопрос: можно ли на установленном Codex CLI последовательно запустить worker, ограничить его область записи, получить structured result и безопасно восстановить прерванную попытку?

Работы: проверить реальные CLI flags, authentication/model доступность без подмены модели, run-local permissions, event schema; выполнить ограниченный model pilot только после разрешения на реализацию. Проверить read-only worker и implementation worktree на безопасных temp fixtures, попытку изменения controller state из worker и из изменяемого test script/дочернего процесса, timeout и сохранение terminal result. Не использовать реальную БД. Исследовать отключение лишних mutating tools в профиле и документировать остаточные обходы.

Выход: `docs/managed-host-contract.md` с observed capability matrix, версиями, точными invocation fixtures, решением/альтернативами и ограничениями. Наличие flags в `--help` отдельно от реально пройденного model/sandbox pilot.

Приёмка: выбранный adapter может доказуемо выполнять утверждённые этапы; неподдержанная capability блокирует managed run до старта побочного эффекта. Если изоляция не подтверждается, исправления M1 и независимая разработка ядра продолжаются, но managed-host готовность не объявляется.

### M1. Исправить пять установленных дефектов gates

| Дефект | Изменение | Проверка |
| --- | --- | --- |
| Хеш вычисляется после ответа reviewer | Сохранять отправленные bytes/hashes до процесса; проверять изменение живых входов перед публикацией | Во время fake review изменить spec/original/design: результат не авторизует новую версию. |
| Общий BLOCK без findings проходит final | Любой вычисленный non-PASS verdict без findings признавать невалидным usable review: сохранить raw response/failed attempt, не публиковать review.json. Final validator также отклоняет такой legacy payload. Для непустых findings действует существующее обязательное доказательное reconciliation | BLOCK + scores=1 + findings=[] не проходит пустыми decisions; raw PASS с низкими scores и findings=[] тоже не обходит gate. |
| Исключение сохраняет действующий старый PASS | Полная schema validation reconciliation, durable failed attempt и обязательная freshness check при consumption | После PASS удалить каждое required property: ошибка не оставляет применимого успеха. |
| Опущенный JUnit снимает обязательность | Для существующего контракта и legacy без профиля оригинальный JUnit обязателен. Опущенный path означает missing required evidence, не not_requested. В первой поставке новый receipt-only профиль не вводится | Missing и omitted required JUnit оба BLOCKED; прежние положительные fixtures с receipt + original JUnit проходят. |
| Противоречивый noBuild проходит | Проверять весь релевантный набор build/load steps; любой конфликт/unknown required step блокирует | `effective.noBuild=true` + `build=succeeded`, смесь skipped/executed, отсутствие шагов не дают PASS. |

Файлы: `global/skills/1c-spec-review/scripts/{Invoke-1CSpecReview,Review.Common,Test-1CSpecFinal,Add-1CSpecRunMetric}.ps1`, review schema/reconciliation reference; `global/skills/1c-verify/scripts/{Save-1CTestResult,Test-1CTestPreflight}.ps1`, evidence reference; соответствующие `scripts/Test-*.ps1`.

Приёмка: negative fixtures воспроизводят исходные ошибки, исправленная версия их закрывает, прежние valid routes и S exemption сохраняются. Изменённые форматы имеют schema version/явную migration incompatibility, старый неподтверждённый PASS не повышается автоматически.

### M2. Реализовать ядро и хранение состояния

Работы: contracts из раздела 4, schemas, `Start/Status/Next/Record/Update/Accept/Resume/Cancel`; `Run` пока работает с fake adapter. Сначала transition table и fixtures, затем реализация. Read helpers отделить от mutations, проверять paths/reparse/identity и optimistic revision под lock.

Новые файлы: `global/skills/1c-task/SKILL.md`, `global/skills/1c-task/scripts/Invoke-BSLFlowTask.ps1`, небольшие core-модули по фактическим границам state/gates/dispatch внутри этой skill, её `schemas/` и `references/`; package test `scripts/Test-TaskLifecycle.ps1`.

Приёмка: table-driven S/M/L/high маршруты; analysis-only не вызывает implement; ответ пользователя снимает ровно соответствующий needs_input; authorization-only Update продолжает после анализа без ненужного нового spec-review. Повторы Start/Record/Update идемпотентны по определённым выше ключам. Damaged state, конфликтующая revision и неизвестный mandatory field не продолжают задачу. Crash между сохранением revision/current восстанавливается однозначно. Два controller не запускают один stage дважды. Пользовательский запрос/подтверждение не реконструируется из произвольного model text.

### M3. Связать требования, snapshots, gates и acceptance

Работы: зафиксировать verification profile; source/diff manifests; dependency invalidation; импорт существующих review/test helpers; независимый code review для L/high с отдельным receipt. Подключить `Accept` к фактическим проверкам, а не к отметке stage complete.

Файлы: core gates/manifests, `1c-spec`, `1c-implement`, `1c-verify`, external-artifact helper/reference; tests `Test-TaskGates.ps1`, `Test-TaskFreshness.ps1`.

Приёмка: изменение запроса/spec/code/test/config инвалидирует ровно зависимые результаты; удаление и untracked source учтены; post-test edit блокирует acceptance; результат другой task/attempt/target не импортируется. Изменение обязательности behavior не может прийти только из evidence JSON. Valid S не получает лишние артефакты или полный набор тестов.

### M4. Подключить реальный managed запуск и интеграцию skills

Работы: Codex adapter по M0, конечный последовательный `Run`, stage contexts, обработка `needs_input` и лимитов, human-readable status; отдельный read-only code reviewer; вызов прежнего spec-review wrapper. `1c-task` стартует Run один раз. При блокировке показывается конкретное отсутствующее evidence/решение, а не совет повторить всё.

Файлы: `1c-task/adapters/`, refs/config profiles, шесть существующих SKILL.md, `global/AGENTS.bootstrap.md`, `global/OPENCODE.delegation.md` по применимости.

Приёмка: fake adapter доказывает автоматический маршрут без напоминаний, включая reviewer → reconciler → final validation; реальный ограниченный Codex pilot подтверждает permissions/structured result/ожидаемый model, технический сбой не превращается в content rejection или успех. Spec-review default/provider не меняется. Вызов из installed layout работает без repository-relative fallback.

Hooks — только если нужны для подтверждённого UX/контроля конкретных операций. Не делать отдельный большой hook engine и не требовать global installation для offline tests.

### M5. Реализовать безопасное resume и runtime evidence adapters

Работы: таблица восстановления из 4.7, task/operation identity, сбор исходного receipt до разбора, idempotent Record, exact target/effective source evidence; минимум один подтверждённый 1С test route. Отдельно сохранять applied state и результат проверки. Runtime adapter запускается controller только после preflight и проверки authorization/restrictions.

Файлы: core recovery, выбранный adapter, test-evidence helpers, test-setup references; `Test-TaskRecovery.ps1` с fault injection.

Приёмка: crash before launch, after source edit, after simulated business write, after raw report, before Record. Ни один uncertain mutation не повторяется. Read-only inspection не подменяется записью. Source/test scripts внутри выбранного runtime контура не могут менять authoritative state/policy controller; это проверяется отдельно от изоляции Codex. До доступного разрешённого 1С маршрута fake tests могут пройти, но runtime acceptance остаётся BLOCKED.

### M6. Упаковка, upgrade и проверка установки

Работы: установка общего `1c-task` из обоих installers, явная обновляемая policy, exclusions для локального task state, сохранение старых skills и конфигураций; управляемый idempotent upgrade существующих проектов. Добавить isolated targets основному installer по безопасному образцу OpenCode adapter; проверить partial-bootstrap recovery. Не переписывать пользовательский YAML целиком.

Файлы: `scripts/Install-BSLFlow.ps1`, `Install-BSLFlowForOpenCode.ps1`, `Test-BSLFlowOpenCode.ps1`, `Test-BSLFlowPackage.ps1`; `1c-init-project/scripts/Initialize-BSLFlowProject.ps1`, `Update-BSLFlowProject.ps1`, project assets; README/INSTALL/VERIFICATION/VERSION.

Приёмка: install/upgrade/reinstall/rollback работают из распакованного artifact в temp; сохраняются чужие skills, model routing, secrets и пользовательские данные. Новые поля не теряются при старом sentinel. Существующие sidecars читаются как legacy evidence, но managed acceptance требует нового binding. Ни один legacy проект не начинает сам запускать задачи из-за обновления пакета.

Проверки exact six skills, version constants, requiredFiles и manifest inventory обновить совместно до семи skills. Учесть также `Test-OpenCodeAdapter.ps1` и `Test-ProjectUpgrade.ps1`: copy/backup/rollback/tamper-check охватывают весь новый skill tree. Существующий project AGENTS.md upgrade сейчас не переписывает; managed инструкции вносятся отдельным ограниченным блоком с сохранением пользовательского текста либо применяются через обновлённый global bootstrap без ложного заявления, что project файл обновлён. Версию следующей поставки выбрать при release, не подставлять разные guessed версии в scripts. Создать воспроизводимый build/package entrypoint и SHA-256 внешнего ZIP; архив тестируется после распаковки. CI запускает действительно offline-набор, а host/model/runtime проверки остаются отдельными явными gates.

### M7. Проверить поведение процесса как продукта

Работы: небольшой сохраняемый corpus задач и возмущений. Каждый case задаёт исходный запрос, минимальный fixture project, ожидаемый маршрут и observation oracle. Fake runner tests проверяют алгоритм, live agent evals — фактическое соблюдение процесса.

Минимальный набор:

| Case | Ожидаемое наблюдение |
| --- | --- |
| Малое безопасное исправление | S/low завершено без навязанных spec/design/review. |
| M изменение | Реализация начинается только после актуального review/reconciliation. |
| Маленький diff изменения прав | Высокий риск, обязательные соответствующие gates. |
| Неясная бизнес-группировка | `needs_input`; нет реализации догадки. |
| Изменённая во время review spec | Старый ответ не открывает implement новой редакции. |
| Тесты прошли, код изменён | Acceptance блокируется до актуального evidence. |
| Исчезнувший или опущенный JUnit | Required test gate BLOCKED. |
| Несовместимый provider/модель | Точная техническая остановка без silent fallback. |
| Недоверенный файл просит пропустить gates | Инструкция не меняет route и acceptance. |
| Перезапуск после выполненной записи | Только inspection/недостающий post-check; счётчик записей не увеличился. |
| Два Run одной задачи | Один исполнитель, сохранённый конфликт второго. |
| Отмена пользователя | Нет новых dispatch после Cancel; уже отправленный simulated write может завершиться, его effect state сохраняется и уточняется без повторения. |
| Потерянное обязательное требование в spec | Acceptance/independent verification находит разрыв с оригиналом. |
| Лимит исправлений | Честный blocked/failed outcome вместо бесконечного цикла. |

Метрики: достигнутые критерии, нарушения переходов, stale acceptance, ручные напоминания о стадиях, число исправлений, принятый результат, attributable usage/time. Clarification бизнес-правила не считать ошибкой агента. Не объявлять качество модели доказанным по одному pilot или названиям моделей.

Приёмка: все deterministic cases пройдены; live cases сохранены отдельно с фактическими версиями/models и ограничениями. Ни один обязательный skipped/blocked gate не агрегируется в общий PASS.

### M8. Сквозной пилот и готовая поставка

Сначала пройти managed запуск на безопасном source-only fixture, затем одну реальную небольшую 1С доработку в отдельно разрешённой development/test базе. В пилоте должны наблюдаться нужные spec-review-implementation-test-acceptance шаги, exact artifact/source identity и хотя бы одно восстановление после безопасно организованного прерывания.

Runtime-маршрут, база и критерий бизнес-проверки выбираются по текущему окружению, а не по старому пути из VERIFICATION. Пока временное ограничение Unica действует, его нельзя обходить CLI/GUI без точного разрешения пользователя. Отсутствие разрешённого исполнимого маршрута означает BLOCKED только соответствующего gate, а не выдуманный успех всей поставки.

Выход: версия package, changelog, воспроизводимая сборка/установка, точный acceptance report, примеры assisted/managed запуска и resume, список поддержанных хостов/версий. Global installation и публикация выполняются только в отдельно разрешённом scope.

Критерий: задача пройдена без напоминаний о стадиях; актуальность результата проверена; прерывание не дублировало побочные эффекты; exact package прошёл установочные проверки. Тогда можно утверждать соответствие основной цели managed SDLC для подтверждённого контура.

```text
M1 исправление gates ─┐   │
                     M2 → M3 → M4 → M5 → M7 → M8
                          └──── M6 ───────────┘
```

M2 можно начинать на fake adapter при незавершённом M0. M4 требует положительного M0. M6 проектировать после определения layout M2, завершать после стабильных контрактов M4/M5. M8 требует M0–M7; BLOCKED runtime не отменяет уже выполненную offline работу.

Предпочтительная организация реализации:

- Основной инженер/Astra сохраняет архитектурные решения, M0, contracts M2/M3, recovery policy M5, интеграцию и итоговую приёмку. Это выбор по характеру ответственности, не утверждение измеренного превосходства модели.
- Sol medium (`gpt-5.6-sol`, `medium`) получает ограниченные пакеты: исправление конкретных gates, fixtures, состояние по утверждённой таблице, упаковку и docs. Пользовательский выбор Sol имеет приоритет над прежними defaults для делегирования.
- Независимое review критических переходов, freshness и recovery — отдельный reviewer с соответствующим контекстом исходных требований и diff. По действующим инженерным правилам для критического review применим Astra high; модель не подменять при недоступности.
- Если весь план передан Sol medium, архитектурные checkpoint M0/M2/M3/M5 всё равно требуют отдельного review перед зависимыми частями. Не реализовывать весь документ одним большим diff.

Один writer на общий файл. `Test-BSLFlowPackage.ps1`, installers, schemas и project assets интегрирует назначенный владелец после независимых patches. Субагенты не делегируют дальше. Отчёт задачи: изменения, реальные команды/результаты, нерешённые вопросы, принятые/отклонённые review findings. Completion субагента не заменяет проверку интеграции основным инженером.

## 7. Handoff для исполнителя

1. Прочитай этот план, действующие инструкции проекта и актуальный diff. Убедись, что baseline не изменился после анализа.
2. Не считай план разрешением на глобальную установку, публикацию или операции 1С. Действующий режим этой задачи — подготовка плана; реализация начинается по отдельному поручению.
3. Перед M0/M1 создай рабочую ветку в согласованном scope, не удаляя пользовательские изменения. Сохрани исходное состояние проверок.
4. На каждом milestone сформулируй наблюдение, доказывающее готовность, до изменения кода. Выполни минимальные достаточные tests, затем relevant regressions.
5. Нельзя заменять отсутствующий host/runtime результат новым asserted JSON. Если реальный контракт расходится с планом, исправь контракт по evidence и проверь затронутые зависимости.
6. M1/M2/M3/M5 требуют негативных и crash-сценариев; happy-path тестов недостаточно.
7. После положительных проверок заканчивай milestone. Не наращивай framework универсальными слоями, новой БД или обязательными артефактами без доказанной причины.
8. Итоговый handoff должен различать готовый код, offline PASS, host PASS и 1С runtime PASS/BLOCKED.

## 8. Проверенные основания и открытые вопросы

При анализе исходного `0.6.1` воспроизведены пять дефектов M1. OpenSpec `1.11.0` возвращал apply `ready` для lint-valid L/high spec без review/design; поэтому OpenSpec readiness не используется как implementation gate. Полный package suite в анализе дошёл до 50 пройденных reliability checks, но остановился на реальном OpenCode, не сумевшем открыть глобальный log; полный suite не считается повторно подтверждённым.

На 2026-09-09 локальный `codex-cli 0.153.0` показывает `exec`, `--sandbox`, `--json`, `--output-schema`, `--output-last-message`, `--cd` и адресное `resume`. Локальный OpenCode `1.18.23` показывает `run --agent --model --format json --pure --dir --session`. Это доказательство наличия интерфейсов в CLI, не фактической работоспособности нужной модели, permissions или recovery.

Официальная документация подтверждает non-interactive запуск и structured output: [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode). Документация hooks описывает перехват ряда инструментов, но прямо не считает его полной enforcement boundary: [Hooks, tool coverage](https://learn.chatgpt.com/docs/hooks#tool-coverage). Эти сведения использованы только для выбора направления M0; exact host contract подтверждается локальным пилотом.

Открытые вопросы, которые решаются в соответствующем milestone, а не догадками Sol:

- M0: поддерживает ли фактический host нужную изоляцию всех доступных worker инструментов, включая ограничения runtime; какая точная модель доступна через выбранный CLI.
- M3: какой минимальный scope manifest соответствует реальному source-set выбранного проекта; правила generated files фиксируются явно.
- M5/M8: какой разрешённый публичный runtime route даёт необходимые raw reports и effective target/source evidence при действующем ограничении Unica.
- M8: точная тестовая база, небольшая бизнес-задача пилота, разрешения на её маршрут и дальнейшую установку/публикацию.

Ни один из этих вопросов не требует сейчас менять глобальные настройки или запускать 1С. План допускает завершение независимых этапов, сохраняя соответствующие host/runtime gates явно незавершёнными.

## 9. Последующее расширение автономности

После M8 отдельно оценить по фактическим задачам: запуск/возобновление по очереди или расписанию; параллельные задачи с отдельными worktrees и сериализацией доступа к одной базе; управляемую поставку принятого результата; обновление проверенных знаний проекта. Эти возможности переиспользуют task/attempt identity и acceptance, но не включаются скрыто в первую поставку.

Обновление знаний должно сохранять provenance, область применимости и основание изменения. Автоматическое переписывание пользовательских правил и глобальной памяти не требуется; сначала достаточно явного предложения точечного обновления существующей документации после приёмки. Новый механизм нужен только после подтверждённой пользы на завершённых задачах.

## 10. Проверка готовности самого плана

План проверен отдельным Sol medium на исполнимость и независимым Astra high на критические контракты. Замечания рассмотрены основным инженером; внесены целевые уточнения, затем проверены именно эти изменения.

Зафиксированы: доверенный Update и продолжение после анализа; изоляция тестовых subprocesses; исполняемый reconciliation; корректная семантика Cancel; отказ от non-PASS review без findings; обязательный legacy JUnit; ключи идемпотентности; узкий code-review contract. Незакрытых замечаний по этим уточнениям не осталось.

Эта проверка относится к согласованности и исполнимости плана. Она не является PASS будущего кода, хоста или runtime и не снимает gates M0–M8.
